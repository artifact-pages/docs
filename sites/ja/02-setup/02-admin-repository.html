管理リポジトリを準備する

管理リポジトリacme/platform-adminに、配信先の設定と、各チームが呼び出す共通のワークフローを用意します。このステップが終わると、チームは短いワークフローを1つ置くだけで公開できるようになります。

  1. 1インフラを構築する
  2. 2管理リポジトリを準備する
  3. 3閲覧アプリをデプロイする
  4. 4サイトを登録する
  5. 5最初のサイトを公開する
  6. 6PRプレビューを使えるようにする

設定ファイルを置く

管理リポジトリの直下にartifact-pages.yamlを作ります。前のステップのTerraformの出力（配信先の設定）を貼り、閲覧アプリとCLIの版と、登録するサイトを書き足します。サイトはステップ4で登録するので、ここでは空にしておきます。

artifact-pages.yaml / Cloudflareの場合（説明用の値）
schemaVersion: 1
provider: cloudflare
cloudflare:                 # terraform output の内容
  accountId: 0123456789abcdef0123456789abcdef
  bucket: artifact-pages
  publicBaseURL: https://docs.example.com
  zoneId: fedcba9876543210fedcba9876543210
cli:
  version: x.y.z
web:
  version: x.y.z
sites: {}
artifact-pages.yaml / AWSの場合（説明用の値）
schemaVersion: 1
provider: aws
aws:                        # terraform output の内容
  accountId: "123456789012"
  bucket: artifact-pages-123456789012-us-east-1
  distributionId: E1ABCDEFGHIJKL
  region: us-east-1
publicBaseURL: https://d111111abcdef8.cloudfront.net   # AWSでは自分で足す
cli:
  version: x.y.z
web:
  version: x.y.z
sites: {}
  • cli.versionとweb.versionは、GitHub ReleasesにあるCLIと閲覧アプリ（web/vx.y.z）の版を、先頭のvを付けずに正確に書きます。2つの版の番号はそろっていなくて構いません。
  • AWSではpublicBaseURLを足します。Terraformの出力には読者が開くURLが含まれません。これがないと、プレビューのURLを作れずにプレビューが失敗します。独自ドメインを使うならそのURLにします。
  • 認証情報の値は書きません。設定ファイルに書けるのは、値を読む環境変数の名前だけです。既定の名前を使うなら、それも書きません。

共通のワークフローを生成する

各チームが呼び出す共通のワークフローは、CLIのregistry setupで生成します。手で書く必要はありません。

ターミナル / 管理リポジトリの直下
$ artifact-pages registry setup --directory . --config artifact-pages.yaml --repository acme/platform-admin
生成されるファイル役割
.github/workflows/publish-site.ymlチームが呼び出す、サイトの公開のワークフロー
.github/workflows/preview-site.ymlチームが呼び出す、PRプレビューのワークフロー
.github/actions/site-sync/action.yml上の2つが使う中身。製品のpublish-actionとpreview-actionを、この管理リポジトリの設定ファイルで呼び出します。
.github/workflows/registry.yml管理リポジトリで、設定の変更をサイトの登録に反映するワークフロー
  • このコマンドは手元のファイルを書くだけです。シークレットを読んだり、GitHubを操作したりはしません。続けて行う設定を、ghのコマンドとして表示します。
  • 使う製品のActionsの版は、実行したCLIの版に組み込まれたものです。設定のcli.versionには切り替わりません。
  • 生成したファイルは手で編集しないでください。直したいときは作り直します（「共通の公開・プレビューの仕組みを更新する」）。
  • 対応する配信先はCloudflareとAWSです。設定ファイルは管理リポジトリの中の通常のファイルである必要があります。

生成したファイルと設定ファイルをコミットし、mainにマージします。

共通のワークフローの動き方

チームのワークフローがuses: acme/platform-admin/.github/workflows/publish-site.yml@mainで呼び出すと、共通のワークフローは、自分と同じコミットにあるartifact-pages.yamlを使って、そのチームのリポジトリを公開します。

項目内容
入力site（必須、サイトID）とenvironment（任意、チームのリポジトリのEnvironmentの名前）。ほかの入力はありません。
動く権限呼び出したチームのリポジトリの権限、シークレット、OIDCで動きます。
本番に書き込むときmainへのプッシュと、mainでの手動実行だけ。プルリクエストなど、それ以外は試し実行です。
プレビュー同じリポジトリのブランチからのプルリクエストだけ。プルリクエストにコメントを付けます。
実行環境GitHubのホストするUbuntuのランナー。

Organizationから呼び出せるようにする

管理リポジトリが非公開の場合は、ActionsのアクセスをOrganizationのリポジトリに開く設定にします。registry setupが表示するコマンドと同じです。それでも、公開リポジトリからは非公開リポジトリの共通のワークフローを呼び出せません。公開リポジトリのチームも使う場合は、管理リポジトリを公開にします。

ターミナル / GitHub CLI
$ gh api --method PUT repos/acme/platform-admin/actions/permissions/access --field access_level=organization

呼び出したチームのリポジトリで共通のワークフローが動くので、そのリポジトリのジョブのログを読める人は、共通のワークフローの実行の様子も読めます。

認証情報を置く

Cloudflare

公開ジョブの認証情報（CF_R2_ACCESS_KEY_ID、CF_R2_SECRET_ACCESS_KEY、CF_API_TOKEN）は、それを使うジョブが動くリポジトリのシークレットに置きます。

  • 管理リポジトリ。登録の反映と閲覧アプリの配置に使います。registry.ymlはプルリクエストではEnvironmentなしで試し実行し、それ以外ではproductionのEnvironmentで動きます。リポジトリのシークレットに置けば両方から読めます。productionのEnvironmentのシークレットだけに置くと、プルリクエストの試し実行が配信先を読めません。
  • 各チームのリポジトリ。共通のワークフローは、呼び出したリポジトリのシークレットを使います（呼び出す側にsecrets: inherit）。管理リポジトリのシークレットはチームのジョブには届きません。Organizationのシークレットにまとめることもできます。

AWS

AWSではシークレットを置かず、各ジョブがIAMロールを引き受けます。管理リポジトリのリポジトリ変数ARTIFACT_PAGES_REGISTRY_ADMIN_ROLE_ARNに、Terraformの出力admin_role_arnを設定します（registry setupがコマンドを表示します）。各チームのジョブのロールは、共通のワークフローがサイトIDと設定のaws.accountIdから求めるので、チームに設定は要りません。Terraformのadmin_github_subjectsとsatellite_github_subjectsに、実際に動くジョブのsubが入っていることを確かめてください。

Environment

本番の書き込みに承認やブランチの制限をかけたい場合は、GitHubのEnvironmentを使います。非公開のリポジトリでEnvironmentを使えるかどうか、承認のルールまで使えるかどうかは、GitHubのプランによって違うので確かめてください。管理リポジトリにはproductionを作ります。チームがenvironment入力で名前を渡すと、共通のワークフローは呼び出したリポジトリのそのEnvironmentを使います。存在しない名前を渡すとGitHubが制限なしで作ってしまうので、先に作っておきます。

共通のワークフローを使わずにCLIで設定を読む

手元のCLIや独自のジョブから、管理リポジトリの設定を直接読むこともできます。--configにgithub://の指定を渡します。

ターミナル
$ artifact-pages site sync --site sre --config 'github://acme/platform-admin/artifact-pages.yaml?ref=main' --dry-run
  • 形はgithub://OWNER/REPO[/FILE]?ref=REFです。FILEを省くとartifact-pages.yaml、refを省くと既定のブランチになります。?を含むので、シェルでは引用符で囲みます。
  • 非公開のリポジトリなら、そのリポジトリのcontents:readを持つトークンをGITHUB_TOKENかGH_TOKENに設定します。GitHub Appのインストールトークンや、fine-grained personal access tokenを使えます。製品のActionsには、別のトークンを渡す入力はありません。
  • 読めないときのメッセージと原因は「問題を調べ、復旧する」にあります。

GitHub Appで非公開の設定を読む

共通のワークフローを使うチームには、この準備は要りません。独自のジョブから非公開の管理リポジトリの設定を直接読む場合に使います。

  1. Organizationで、Contentsの読み取り（contents:read）だけを持つGitHub Appを作り、管理リポジトリにだけインストールします。
  2. ジョブを動かすリポジトリに、AppのIDと秘密鍵をシークレットとして置きます。
  3. ジョブの中で、管理リポジトリを対象にしたインストールトークンを発行し（たとえばactions/create-github-app-tokenを使います）、CLIを動かすステップの環境変数GITHUB_TOKENに渡します。
  4. CLIの--configに、上のgithub://の指定を渡します。

製品のActionsにはトークンを渡す入力がないので、この方法はCLIを直接動かすジョブに限ります。
