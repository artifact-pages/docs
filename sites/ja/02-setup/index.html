導入する

この章では、配信環境を作るところから始めて、最初のチームが自分のリポジトリから資料を公開し、プルリクエストのプレビューで確かめられるところまで進めます。全体を通して、同じ説明用の例を使います。

到達する状態

  • CloudflareかAWSに配信環境があり、閲覧アプリが置かれている。
  • 管理リポジトリacme/platform-adminに、設定ファイルと、各チームが呼び出す共通の公開・プレビューのワークフローがある。
  • チームのリポジトリacme/sreのサイトsreが登録され、マージすると公開され、プルリクエストにはプレビューが付く。

リポジトリとサイトの名前は説明用の例です。お使いの名前に置き換えて読んでください。

全体の流れ

ステップ行う人終わったときの状態
1. インフラを構築する管理者ストレージ、ホスト名、配信の規則、認証情報がそろい、配信先の設定が手元にある
2. 管理リポジトリを準備する管理者設定ファイルと共通のワークフローが管理リポジトリにある
3. 閲覧アプリをデプロイする管理者ホスト名を開くと閲覧アプリが表示される
4. サイトを登録する管理者サイトsreが一覧に出る（まだ資料はない）
5. 最初のサイトを公開するチームacme/sreの資料が読める
6. PRプレビューを使えるようにするチームプルリクエストにプレビューのコメントが付く

2種類のリポジトリ

管理リポジトリは環境に1つで、配信先の設定、登録するサイトの一覧、CLIと閲覧アプリのバージョン、共通のワークフローを持ちます。チームのリポジトリ（サテライトリポジトリ）はいくつでもあり、公開する資料のディレクトリと、共通のワークフローを呼び出す短いワークフローを持ちます。チームのリポジトリに設定ファイルは置きません。

サイトの登録は、どのリポジトリのどのディレクトリがそのサイトに公開してよいかを決めるものです。読者を限定するものではありません。

事前に用意するもの

  • CloudflareかAWSのアカウント。必要な権限は「インフラを構築する」にあります。
  • GitHubのOrganization。管理リポジトリとチームのリポジトリを同じOrganizationに置きます。共通のワークフローは同じOrganizationの中から呼び出す前提です。既定のブランチはmainにします。共通のワークフローはmainからの実行だけを本番の書き込みにします。
  • 手元のCLI。管理者の作業（共通のワークフローの生成、試し実行）で使います。

CLIを入れる

CLIはGitHub Releasesから、LinuxとmacOS（amd64、arm64）向けの単体のバイナリを入れます。Windows向けはありません。x.y.zは使うリリースの版で、先頭のvは付けません。

ターミナル / インストール
$ VERSION=x.y.z
$ OS=$(uname -s | tr '[:upper:]' '[:lower:]')
$ ARCH=$(uname -m | sed -e 's/x86_64/amd64/' -e 's/aarch64/arm64/')
$ BASE=https://github.com/artifact-pages/artifact-pages/releases/download/v$VERSION
$ curl -fsSLO "$BASE/artifact-pages_v${VERSION}_${OS}_${ARCH}"
$ curl -fsSLO "$BASE/artifact-pages_v${VERSION}_checksums.txt"
$ grep "artifact-pages_v${VERSION}_${OS}_${ARCH}\$" "artifact-pages_v${VERSION}_checksums.txt" | shasum -a 256 -c -
$ install -m 0755 "artifact-pages_v${VERSION}_${OS}_${ARCH}" ~/.local/bin/artifact-pages
$ artifact-pages version
  • チェックサムの確認でOKと出ないバイナリは使わないでください。shasumがないLinuxではsha256sum -c -を使います。
  • ~/.local/binは一例です。PATHの通ったディレクトリに置きます。
  • 入れたCLIは入口です。設定ファイルにcli.versionがあれば、ほとんどのコマンドはその版をダウンロードして確かめ、そちらで実行します。

コマンドの多くは--dry-runで試し実行ができます。試し実行は配信先を読みますが、書き込み、削除、ロック、キャッシュの変更はしません。結果は通常は文章で、--format jsonで機械向けに出せます。

クラウドの前にローカルで試す

配信環境を作る前に、手元のディレクトリを配信先にして、公開から閲覧までを試せます。クラウドのアカウントは要りません（リリースのダウンロードにネットワークは要ります）。プレビューの保持期間、権限、CDN、閲覧の制限は試せません。

  1. 試すリポジトリ（説明用の例ではacme/sreのクローン）の直下に、次の設定ファイルを置きます。repositoryはそのリポジトリのoriginと同じにし、sourcePathは公開したい資料のディレクトリにします。
artifact-pages.yaml / 試すリポジトリ（説明用の例）
schemaVersion: 1
provider: local
local:
  root: .local/storage   # 公開元の外に置く
cli:
  version: x.y.z
web:
  version: x.y.z
sites:
  sre:
    name: SREチーム
    repository: acme/sre
    sourcePath: docs
  1. 閲覧アプリを置き、サイトを登録し、サイトを公開します。それぞれ試し実行で確かめてから実行します。
ターミナル / 試すリポジトリ
$ artifact-pages app deploy --config artifact-pages.yaml
$ artifact-pages registry sync --config artifact-pages.yaml
$ artifact-pages site sync --site sre --config artifact-pages.yaml
  1. .local/storageをWebサーバーで配信して開きます。ファイルをそのまま返すだけのサーバーでは足りません。/_indexes/、/_artifacts/、/_previews/、/assets/はファイルを返してなければ404、/_control以下は返さず、それ以外のURLはすべて/index.htmlを返す設定にします。
nginx / server ブロックの例
root /srv/artifact-pages;   # .local/storage を読み取り専用で置いた場所
location = /_control { return 404; }
location ^~ /_control/ { return 404; }
location ^~ /_indexes/  { try_files $uri =404; }
location ^~ /_artifacts/ { try_files $uri =404; }
location ^~ /_previews/ { try_files $uri =404; }
location ^~ /assets/ { try_files $uri =404; }
location / { try_files $uri $uri/ /index.html; }

この試し方では、共通のワークフローの生成（registry setup）は使えません。クラウドで導入するときは、ステップ1から進めます。
