最初のサイトを公開する

ここからはチームの作業です。acme/sreに公開する資料のディレクトリと、共通のワークフローを呼び出すワークフローを置きます。プルリクエストでは試し実行、mainへのマージで公開されます。

公開するディレクトリを整える

登録したsourcePath（例ではdocs）の中身が、そのままサイトになります。

acme/sre（説明用の例）
docs/
├── README.md              # サイトのトップの Overview になる
├── runbooks/
│   ├── README.md          # フォルダの画面に表示される
│   └── on-call.html
└── postmortems/
    └── 2026-09-db-failover.md
  • そのまま配信できる形にしておきます。Artifact Pagesは生成やビルドをしません。ほかのツールで生成するなら、公開の前のステップで生成します。
  • 公開したくないものは入れません。このディレクトリの中のファイルは、リンクされていなくても、Gitで追跡していなくても公開されます。.htmlのテンプレートや部分的なファイルも資料として載ります。シンボリックリンクがあると公開は失敗します。.gitは公開されません。
  • サイトのトップ。直下のREADME.md（なければindex.md）が、サイトのトップのOverviewになります。直下のindex.htmlはその代わりにはならず、/sre/index.htmlという資料として開きます。
  • URL。資料のURLは/sre/に続けて、このディレクトリからのパスを拡張子まで付けたものです。

ワークフローを置く

.github/workflows/publish.yml / acme/sre
name: Publish docs
on:
  pull_request:
    paths: ['docs/**']
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
concurrency:
  group: publish-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
jobs:
  publish:
    permissions:
      contents: read
      # AWSでは id-token: write も足す
    uses: acme/platform-admin/.github/workflows/publish-site.yml@main
    with:
      site: sre
      environment: ${{ github.event_name != 'pull_request' && 'production' || '' }}
    secrets: inherit
  • siteは登録したサイトIDです。environmentは、使うならこのリポジトリのEnvironmentの名前で、この例ではプルリクエストのときだけ空にしています。Environmentを使わないなら、この行ごと省きます。
  • 共通のワークフローはsiteとenvironmentしか受け取りません。dry-runやfetch-depthなどをwithで渡すことはできません。
  • Cloudflareでは、このリポジトリ（またはOrganization）のシークレットに公開用の認証情報を入れておきます。AWSでは、このジョブのsubがTerraformのsatellite_github_subjectsに入っている必要があります。

試し実行してから公開する

  1. 資料とワークフローを追加するプルリクエストを出します。ジョブは試し実行で、何が書き込まれるかがジョブの概要に出ます。
  2. マージすると、mainへのプッシュで公開されます。結果はsynced、何も変わっていなければno-opです。
  3. 閲覧アプリでSREチームのサイトを開き、資料が読めることを確かめます。

公開は、新しいファイルと変わったファイルを書き込み、一覧と検索のデータを更新し、なくなったファイルを削除します。手元から試すときは、管理リポジトリの設定をgithub://で読みます（AWSでは手元にもAWSの認証が要ります）。

ターミナル / acme/sre
$ artifact-pages site sync --site sre --config github://acme/platform-admin/artifact-pages.yaml --dry-run

--sourceを省くと、登録したsourcePathを公開します。--refは資料に記録する参照の表示を変えるだけで、公開するファイルは変えません。

浅いチェックアウトと日付

資料の更新日と名前は、Gitの履歴から求めます。GitHub Actionsのチェックアウトは既定で直近の1コミットだけですが、CLIは必要なだけ履歴を取り寄せるので、通常は全履歴があるときと同じ結果になります。

ただし、前回の公開から内容が同じ状態に戻ったファイル（変更を取り消したコミットなど）は、前回の更新日のまま残ることがあります。どんな場合も履歴どおりの日付にしたいときは、全履歴でチェックアウトします。共通のワークフローはfetch-depthを受け取らないので、その場合は製品のpublish-actionを直接使う構成にします。

管理リポジトリとサイトが同じリポジトリの場合

小さな組織や試験的な導入では、管理リポジトリの中のディレクトリを1つのサイトとして公開することもできます。この場合は、共通のワークフローを通さずに、製品のpublish-actionを同じリポジトリの設定ファイルで直接呼び出せます。

.github/workflows/publish.yml / 管理とサイトが同じリポジトリ（Cloudflare）
jobs:
  publish:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
    steps:
      - uses: artifact-pages/publish-action@vX.Y.Z
        with:
          site: sre
          config: artifact-pages.yaml
          publish-on: |
            push:refs/heads/main
        env:
          CF_R2_ACCESS_KEY_ID: ${{ secrets.CF_R2_ACCESS_KEY_ID }}
          CF_R2_SECRET_ACCESS_KEY: ${{ secrets.CF_R2_SECRET_ACCESS_KEY }}
          CF_API_TOKEN: ${{ secrets.CF_API_TOKEN }}
  • publish-onに合わないきっかけ（プルリクエストなど）では試し実行になります。
  • sourcePathはdocsのように資料だけのディレクトリにします。リポジトリ全体にすると、設定ファイルやワークフローも公開されます。
  • この場合も、登録の反映と閲覧アプリの配置は別のジョブで行います。
