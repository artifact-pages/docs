閲覧アプリをデプロイする

読者が開く閲覧アプリを、配信先に置きます。置くのは設定ファイルのweb.versionで選んだリリースです。共通のワークフローは閲覧アプリの配置を含まないので、管理リポジトリに配置用のワークフローを1つ書きます。

  1. 1インフラを構築する
  2. 2管理リポジトリを準備する
  3. 3閲覧アプリをデプロイする
  4. 4サイトを登録する
  5. 5最初のサイトを公開する
  6. 6PRプレビューを使えるようにする

配置のワークフローを書く

閲覧アプリの配置は、必要なときに手動で動かす形にします。設定を変えたりActionsを更新したりしただけでは配置されないので、意図しない更新が起きません。

.github/workflows/app-deploy.yml / 管理リポジトリ（Cloudflare）
name: App deploy
on:
  workflow_dispatch:
    inputs:
      dry-run:
        description: Plan only, without writes.
        type: boolean
        default: true
permissions:
  contents: read
concurrency:
  group: app-deploy
  cancel-in-progress: false
jobs:
  deploy:
    runs-on: ubuntu-24.04
    environment: production
    steps:
      - uses: artifact-pages/app-deploy-action@vX.Y.Z
        with:
          dry-run: ${{ inputs.dry-run }}
        env:
          CF_R2_ACCESS_KEY_ID: ${{ secrets.CF_R2_ACCESS_KEY_ID }}
          CF_R2_SECRET_ACCESS_KEY: ${{ secrets.CF_R2_SECRET_ACCESS_KEY }}
          CF_API_TOKEN: ${{ secrets.CF_API_TOKEN }}
  • vX.Y.Zはapp-deploy-actionのリリースの版です。生成された共通のワークフローと同じように、タグの代わりにコミットのSHAで固定するとより確実です。Actionの版は、置く閲覧アプリの版とは関係ありません。閲覧アプリはweb.versionで決まります。
  • AWSではenvの代わりに、このステップの前にaws-actions/configure-aws-credentialsでadmin_role_arnのロールを引き受け、ジョブのpermissionsにid-token: writeを足します。

試し実行してから置く

  1. GitHubのActionsの画面からApp deployを、dry-runにチェックを入れたまま動かします。何を書き込むかが表示され、結果はplannedになります。
  2. 内容がよければ、dry-runのチェックを外してもう一度動かします。結果はdeployedになります。置くものが前回と同じならno-opです。

手元からは、同じことを次のコマンドで行えます。

ターミナル / 管理リポジトリ
$ artifact-pages app deploy --config artifact-pages.yaml --dry-run
$ artifact-pages app deploy --config artifact-pages.yaml

配置では、web/vx.y.zのリリースのアーカイブとチェックサムを確かめてから、閲覧アプリのファイル（index.html、assets/など）を書き込みます。サイトの資料、一覧、プレビューには触れません。index.htmlは最後に書き込みますが、すべてのファイルが一瞬で切り替わるわけではありません。

開いて確かめる

配信先のホスト名を開きます。CloudflareではpublicBaseURL、AWSではCloudFrontのホスト名（独自ドメインならそのホスト名）です。閲覧アプリが表示されれば配置は完了です。まだサイトを登録していないので、サイトの一覧は空です。
