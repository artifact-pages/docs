AWSに構築する

S3のバケットとCloudFrontで、Artifact Pagesの配信環境を作ります。公開ジョブが使うIAMロールもモジュールが作り、各ジョブはGitHubのOIDCでそのロールを引き受けます。GitHubにAWSのアクセスキーは置きません。

  1. 1インフラを構築する
  2. 2管理リポジトリを準備する
  3. 3閲覧アプリをデプロイする
  4. 4サイトを登録する
  5. 5最初のサイトを公開する
  6. 6PRプレビューを使えるようにする

できあがるもの

  • 非公開のS3バケット。パブリックアクセスはブロックし、CloudFrontだけが読めるようにします。閲覧アプリと公開されたArtifactはすべてここに入ります。
  • CloudFrontのディストリビューション。ページのURLを閲覧アプリへ振り分け、配信するファイルの区分ごとのキャッシュと応答ヘッダーを設定します。Artifactのファイルを直接指すURLで、そのファイルがない場合は404を返します。
  • PRプレビューの保持期間。バケットのライフサイクルの規則として、_previews/以下を指定日数で削除します。
  • IAMロール。管理リポジトリ用のロール1つと、サイトごとのロールです（IAMロールとOIDC）。

DNSのレコード、ACMの証明書、GitHub ActionsのOIDCプロバイダー、GitHubのEnvironmentとシークレットは、モジュールが作りません。

先に必要なもの

  • GitHub ActionsのOIDCプロバイダー。同じAWSアカウントに登録しておき、そのARNをモジュールに渡します。ARNのアカウントが適用先のアカウントと違うと、計画の段階で止まります。
  • Terraformを適用できる権限。S3、CloudFront、IAM（ロールとインラインポリシーの作成、OIDCプロバイダーの読み取り）を操作し、WAFを使う場合はWAFv2も操作します。適用に必要な最小限のIAMポリシーは、まだ示せていません。検証は広い管理者権限で行いました。
  • CLI 0.4.0以降。サイトのロールは、各サイト用の制御の領域だけに書き込めます。これを使うのはCLI 0.4.0以降です。

適用に使う権限と、公開ジョブが引き受けるロールは別のものです。混同しないでください。

IAMロールとOIDC

モジュールが作るロールは2種類だけです。

ロール名前使うジョブとできること
管理用<name_prefix>-admin-publisher管理リポジトリのジョブ。閲覧アプリの配置、サイトの登録と登録の取り消し、内部の記録の更新、CloudFrontのキャッシュの無効化。閲覧アプリの配置専用のロールはありません。
サイトごと<name_prefix>-<サイトID>-publisherそのサイトを公開するチームのジョブ。自分のサイトの公開と、PRプレビューの公開と削除。書けるのは自分のサイトの領域だけで、ほかのサイト、サイトの登録情報、閲覧アプリには書けません。プレビュー専用のロールはありません。

サイトごとのロールの名前が64文字を超える場合は、ハッシュを使った名前になります。name_prefixの既定はartifact-pagesです。

各ロールは、GitHubのOIDCトークンのaud（sts.amazonaws.com）とsubが完全に一致するときだけ引き受けられます。モジュールはワイルドカードを足さず、ブランチやEnvironmentを推測もしないので、許可するジョブのsubをすべて正確に書きます。

許可するジョブを書く

Environmentを使うジョブのsubは、既定ではrepo:OWNER/REPO:environment:ENVの形です。Environmentを使わないジョブでは、末尾がジョブのきっかけで変わります。ブランチへのプッシュなら:ref:refs/heads/main、プルリクエストなら:pull_request、タグなら:ref:refs/tags/…のようになります。リポジトリによっては、オーナーとリポジトリのIDを含む別の形を使います。実際の形は次のコマンドで確かめられます。

ターミナル / GitHub CLI
$ gh api repos/OWNER/REPO/actions/oidc/customization/sub --jq '.sub_claim_prefix'

表示されたプレフィックスにジョブの部分（:environment:ENVなど）を足したものを書きます。リポジトリが独自のテンプレートを使っている場合は、プレフィックスから推測せず、試しのジョブで実際のsubを確かめてください。

このガイドの例では、Environmentの名前を管理リポジトリでもチームのリポジトリでもproductionにそろえ、プルリクエストのジョブはEnvironmentを使いません。そのため、許可するsubはリポジトリごとに次の2つです。

ジョブEnvironment許可するsub
管理リポジトリ：mainでの登録の反映、閲覧アプリの配置productionrepo:acme/platform-admin:environment:production
管理リポジトリ：プルリクエストでの登録の試し実行なしrepo:acme/platform-admin:pull_request
チームのリポジトリ：mainでの公開productionrepo:acme/sre:environment:production
チームのリポジトリ：プルリクエストでの試し実行とプレビューなしrepo:acme/sre:pull_request

チームのリポジトリが管理リポジトリの共通のワークフローを呼び出しても、subに入るのは呼び出したチームのリポジトリと、そのリポジトリのEnvironmentです。試し実行も配信先を読むのでロールを引き受けます。プルリクエストのsubは、最初のプルリクエストを出す前から必要です。

Environment

Environmentは、ジョブを初めて動かす前に作り、ブランチの制限をかけておきます。ワークフローに存在しないEnvironmentの名前を書くと、GitHubはそれを制限なしで自動的に作ります。

サイトを登録しただけでは、そのサイトのロールは増えません。新しいサイトを加えるときは、Terraformのsatellite_github_subjectsにも加えて適用します。

モジュールを呼び出す

呼び出し側のTerraformの設定に、モジュールとプロバイダー、あとで使う出力を書きます。最初のチームのサイトもここで加えておくと、次のステップでそのまま公開まで進めます。リポジトリとサイトは説明用の例です。

HCL / main.tf
provider "aws" {
  region = "us-east-1"    # aws_region と同じリージョン
}

module "artifact_pages" {
  source  = "artifact-pages/artifact-pages/aws"
  version = "0.1.1"

  aws_region             = "us-east-1"
  preview_retention_days = 14

  github_oidc_provider_arn = "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"

  admin_github_subjects = [
    "repo:acme/platform-admin:environment:production",   # mainでの登録の反映、閲覧アプリの配置
    "repo:acme/platform-admin:pull_request",            # プルリクエストでの登録の試し実行
  ]

  satellite_github_subjects = {
    sre = [
      "repo:acme/sre:environment:production",   # mainでの公開
      "repo:acme/sre:pull_request",             # プルリクエストでの試し実行とプレビュー
    ]
  }
}

output "aws_deployment_config_yaml" {
  value = module.artifact_pages.aws_deployment_config_yaml
}
output "admin_role_arn" {
  value = module.artifact_pages.admin_role_arn
}
output "satellite_role_arns" {
  value = module.artifact_pages.satellite_role_arns
}
output "distribution_domain_name" {
  value = module.artifact_pages.distribution_domain_name
}

プロバイダーのバージョンはhashicorp/awsの~> 6.0を指定します。

入力内容
aws_region必須S3のバケットを置くリージョン。プロバイダーのregionと同じにします。
preview_retention_days必須PRプレビューを残す日数。1から36500までの整数で、既定値はありません。14は例です。
github_oidc_provider_arn必須登録済みのOIDCプロバイダーのARN。
admin_github_subjects必須管理用ロールを引き受けてよいジョブのsub。1つ以上。
satellite_github_subjects任意サイトIDごとに、そのサイトのロールを引き受けてよいジョブのsub。既定は空で、サイトのロールは作られません。
name_prefix任意ロールの名前の先頭。既定はartifact-pages。変えた場合は、CLIの設定のaws.namePrefixも同じにします。
bucket_name任意既定はartifact-pages-<アカウントID>-<リージョン>。S3の名前は全体で一意なので、使えるとは限りません。
viewer_protocol_policy任意既定のredirect-to-httpsはHTTPをHTTPSへリダイレクトし、https-onlyはHTTPを拒否します。

すべての入力は、モジュールのREADMEにあります。

ホスト名と独自ドメイン

独自ドメインを指定しなければ、CloudFrontが割り当てるホスト名（例：https://d111111abcdef8.cloudfront.net）で読めます。証明書もDNSも要らないので、まずはこれで始められます。ホスト名は出力distribution_domain_nameで確かめます。

独自ドメインを使う場合は、次の順に進めます。

  1. us-east-1にACMの証明書を作り、発行済みになるまで待ちます。
  2. モジュールのaliasesにホスト名を、acm_certificate_arnに証明書のARNを指定して適用します。
  3. DNSをディストリビューションに向けます。Route 53では、distribution_domain_nameとdistribution_hosted_zone_idを使ったエイリアスのA・AAAAレコードを作ります。ほかのDNSではCNAMEをdistribution_domain_nameに向けます。CloudflareのDNSでは、プロキシを通さないDNSのみのレコードにします。

Route 53で証明書からレコードまでまとめて作る例は、モジュールのroute53-consumerにあります。

閲覧を制限する

社内からだけ読めるようにしたい場合は、waf_custom_rulesのプリセットip_allowlistで、一覧にないIPアドレスからの通信を拒否できます。モジュールがAWS WAFのACLを作り、ディストリビューション全体に付けます。独自ドメインだけでなく、CloudFrontのホスト名、プレビュー、キャッシュから返る応答にも効きます。

HCL / module "artifact_pages" に追加
viewer_protocol_policy = "https-only"
waf_custom_rules = {
  presets = {
    ip_allowlist = ["192.0.2.10/32", "2001:db8::/128"]   # 説明用のアドレス。実際の社内の公開CIDRに置き換える
  }
}
  • HTTPSだけを許すのはWAFではなくviewer_protocol_policyの役目です。
  • 自分で管理しているWAFのACLを付けたい場合は、代わりにweb_acl_arnを指定します。2つは同時に指定できません。
  • 自分の接続元のアドレスが一覧に入っていることを、適用の前に確かめてください。
  • WAFを使うと、その分の費用がかかります。

この制限は、IPアドレスで絞るフィルターです。誰が読んでいるかは確かめません。人単位の認証が必要な場合は、別の仕組みを用意してください。WAFの細かな設定は、モジュールのWAFの説明にあります。

計画を確かめて適用する

ターミナル / 呼び出し側のディレクトリ
$ terraform init
$ terraform plan
$ terraform apply

計画で、作られるバケット、ディストリビューション、ロールとそのポリシーを確かめます。WAFを使わずサイトが1つの場合、作られるリソースは22個です。CloudFrontの変更は、適用が終わってから全体に行き渡るまでに時間がかかります。

S3とCloudFrontは使った分だけ課金されます。適用の前に、想定する量でS3とCloudFrontの料金を確かめてください。費用の生まれ方は「コストとパフォーマンス：AWS」で説明します。

プレビューの削除はS3が非同期に行うので、指定した日数ちょうどで消えるとは限りません。プレビューを今すぐ見えなくする手段としては使えません。

出力を次のステップに渡す

次のステップでは、配信先の設定と、ジョブが引き受けるロールのARNを使います。秘密の値は出力に含まれません。

ターミナル / 出力の例
$ terraform output -raw aws_deployment_config_yaml
"aws":
  "accountId": "123456789012"
  "bucket": "artifact-pages-123456789012-us-east-1"
  "distributionId": "E1ABCDEFGHIJKL"
  "region": "us-east-1"
"provider": "aws"
"schemaVersion": 1
$ terraform output -raw admin_role_arn
$ terraform output -json satellite_role_arns
出力使う場所
aws_deployment_config_yaml管理リポジトリのartifact-pages.yamlの配信先の設定。name_prefixを変えた場合だけnamePrefixが加わります。
admin_role_arn管理リポジトリのジョブが引き受けるロール。
satellite_role_arnsサイトIDごとの、各チームのジョブが引き受けるロール。
distribution_domain_name読者が開くホスト名。独自ドメインではCNAMEの向け先。

ロールのARNは設定ファイルには書かず、ジョブの設定で使います。次のステップで、設定ファイルにCLIと閲覧アプリのバージョン、登録するサイトを書き足し、ジョブを用意します。閲覧アプリやサイトを置いたあとの動作の確認も、次のステップ以降で行います。
