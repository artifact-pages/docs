社内展開と運用

新しいチーム・サイトを受け入れる

2つ目以降のチームを受け入れるときに必要なのは、サイトの登録、配信先の権限、チームのワークフローの3つだけです。環境はすでにあるので作り直しません。ここでは、説明用の例としてacme/billingのサイトbillingを受け入れます。

1. サイトを登録する

多くの組織では、チームが管理リポジトリにプルリクエストを出し、管理者がレビューしてマージします。この流れは製品の機能ではなく運用の取り決めなので、組織に合わせて決めてください。追加するのはsitesの1項目です。

artifact-pages.yaml / 管理リポジトリ（説明用の例）
sites:
  sre:                 # 既存のサイトは消さずに残す
    name: SREチーム
    repository: acme/sre
    sourcePath: docs
  billing:
    name: 決済チーム / Billing
    description: 請求まわりの設計と運用
    repository: acme/billing
    sourcePath: docs
  • サイトID（ここではbilling）は、英小文字と数字をハイフンでつないだ形です。assetsは使えません。IDはURLの一部になり、あとから名前を付け替える操作はありません。
  • repositoryはowner/repositoryの形で書きます。URLや.gitは付けません。
  • sourcePathはリポジトリの中の相対パスです。リポジトリ全体なら.です。同じリポジトリとディレクトリの組を、2つのサイトに登録することはできません。

マージしたら、登録を配信先に反映します。sitesは追加分ではなく登録するサイトのすべてなので、既存のサイトを消していないことを試し実行で確かめます。

ターミナル / 管理リポジトリ
$ artifact-pages registry sync --config artifact-pages.yaml --dry-run
$ artifact-pages registry sync --config artifact-pages.yaml

管理リポジトリのワークフローで反映している場合は、そのワークフローがマージ後に同じことを行います。

2. 配信先の権限を足す

AWS

サイトを登録しても、そのサイトのIAMロールはできません。Terraformのsatellite_github_subjectsに新しいサイトIDと、ロールを引き受けてよいジョブのsubを足して適用します。

HCL / module "artifact_pages"（説明用の例）
satellite_github_subjects = {
  sre     = ["repo:acme/sre:environment:artifact-pages-production"]
  billing = [
    "repo:acme/billing:environment:artifact-pages-production",
    "repo:acme/billing:pull_request",   # プレビューのジョブ
  ]
}

ロールはsubが完全に一致するジョブにしか引き受けられません。本公開のジョブ、プレビューのジョブなど、実際に動くジョブのsubをすべて書きます。Environmentを付けないプルリクエストのジョブのsubは、Environmentの例とは形が違います（「許可するジョブを書く」）。ロールのARNは次のコマンドで確かめられます。

ターミナル / 管理リポジトリ
$ artifact-pages registry role-arn --config artifact-pages.yaml --site billing

Cloudflare

チームのリポジトリ（またはOrganization）のシークレットに、公開用の認証情報を入れます。名前はCF_R2_ACCESS_KEY_ID、CF_R2_SECRET_ACCESS_KEY、CF_API_TOKENで、APIトークン1つの方式ならCF_API_TOKENだけです。バケット全体に書ける認証情報は、チームのジョブをそのサイトの領域だけに限りません。限る場合は、サイトのプレフィックスに絞った一時的な認証情報を、組織の仕組みで発行して渡します（「認証情報」）。

3. チームにワークフローを渡す

チームのリポジトリには、管理リポジトリの共通のワークフローを呼び出すファイルを置きます。最初のチームと同じ形で、サイトIDだけが違います。

.github/workflows/publish.yml / acme/billing（説明用の例）
name: Publish docs
on:
  push:
    branches: [main]
  workflow_dispatch:
jobs:
  publish:
    permissions:
      contents: read
      id-token: write   # AWSのときだけ
    uses: acme/platform-admin/.github/workflows/publish-site.yml@main
    with:
      site: billing
      environment: artifact-pages-production   # Environmentを使わないなら省く
    secrets: inherit
  • 呼び出す側のpermissionsが、共通のワークフローで使える権限の上限になります。AWSではOIDCのためにid-token: writeが要ります。
  • 共通のワークフローは、チームのリポジトリの権限とシークレットで動きます。secrets: inheritで、チームのシークレットを共通のワークフローへ渡します。管理リポジトリのシークレットは使われません。
  • 書き込むのは、mainへのプッシュと、mainでの手動実行のときだけです。それ以外のきっかけでは試し実行になります。
  • Environmentを使う場合は、最初に動かす前にチームのリポジトリでEnvironmentを作り、ブランチの制限をかけておきます。

プレビューも同じようにpreview-site.ymlを呼び出します。書き方は「PRプレビューを使えるようにする」と同じです。

4. 最初の公開を確かめる

チームのワークフローを手動で動かすか、mainにマージして、公開が成功することを確かめます。失敗した場合は、まず次の2つを疑います。

メッセージ原因
site "billing" is not registered in the deployed registry登録を配信先に反映していません（registry sync）。
site "billing" is registered to …; selected checkout is …公開しようとしたリポジトリかディレクトリが、登録と違います。

閲覧アプリのサイトの一覧に新しいサイトが出て、資料が読めれば受け入れは完了です。
