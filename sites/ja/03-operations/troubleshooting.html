社内展開と運用

問題を調べ、復旧する

ほとんどの失敗は、同じ操作をもう一度実行すれば収まるように作られています。まず何が失敗したかを確かめ、必要ならロックを解いてから、元の操作をやり直します。

まず切り分ける

  1. 失敗したジョブの概要（Job Summary）で、実行されたCLIの版（CLI executed）、操作、結果、エラーを確かめます。
  2. 終了コードを見ます。2は引数や設定の誤り、1は配信先、ダウンロード、互換性の確認などの失敗です。
  3. 同じ操作を--dry-runで動かします。試し実行は読み取りだけを行い、ロックも取らず、何も書き込みません。

ロックが残っている

同じサイトへの操作は、ロックで1つずつ順に行われます。ロックは自動では期限切れになりません。操作が途中で強制終了されるとロックが残り、次の操作は10秒待ってからtimed out waiting for site "…" lockで失敗します。

ターミナル
# ロックの状態を見る（共有のロックは --scope registry か --scope application）
$ artifact-pages lock inspect --site sre --config artifact-pages.yaml --format json
# 表示された etag を指定して解く
$ artifact-pages lock recover --site sre --observed-etag ETAG --config artifact-pages.yaml
  • 解く前に、本当に誰も動いていないかを確かめます。サイトのロックは、そのサイトの公開とプレビュー、サイトを変えるregistry sync、app deployが取ります。管理リポジトリだけでなく、各チームのジョブや手元の実行も確かめます。取った時刻だけで古いと判断しないでください。
  • lock recoverに試し実行はありません。確かめたetagと今の状態が違えば、何もせずに失敗します。
  • 解くのはロックだけです。そのあとで、止まっていた元の操作をもう一度実行します。

公開や配置が途中で止まった

公開は多数のファイルの書き込みで、途中で失敗しても自動では元に戻りません。同じ公開元と設定で、同じ操作をもう一度実行すれば、残りを書き込んで収まります。

止まった操作やり直すこと
サイトの公開同じsite sync。キャッシュの削除だけが残っていた場合は、変更がなくても結果がsyncedになります。
登録の反映、サイトの取り下げ同じ設定でregistry sync。
閲覧アプリの配置同じapp deploy。

キャッシュの削除に失敗したときのメッセージはsite origin synchronized but cache revalidation failed; retry site publish: …です。ここにあるsite publishは古いコマンド名で、実行するのはsite syncです。

配信先の中身がずれている

誰かが配信先のファイルを直接消したり置き換えたりすると、公開の内容とずれます。通常の公開は、公開元が前回と同じなら配信先の個々のファイルを確かめずにno-opで終わるので、このずれには気付きません。

ターミナル / チームのリポジトリ
$ artifact-pages site sync --site sre --config artifact-pages.yaml --reconcile --dry-run
$ artifact-pages site sync --site sre --config artifact-pages.yaml --reconcile

--reconcileは、配信先のファイルの一覧とメタデータを公開元と突き合わせ、足りないファイル、余分なファイル、メタデータの違いを直します。ファイルの中身までは読まないので、メタデータを保ったまま中身だけが壊れた場合は見つけられません。公開した内容そのものが間違っている場合は、正しいコミットを取り出して公開し直します。--refは表示用の情報を変えるだけで、公開する内容は変えません。

設定を読めない、認証に失敗する

別のリポジトリの設定を読めない

github://で管理リポジトリの設定を直接読む場合、失敗するとcannot read deployment config github://…で始まるメッセージが出ます。

HTTP考えられる原因
401トークンが無効か期限切れ。
403トークンにそのリポジトリのcontents:readがない、またはAPIのレート制限。
404ファイルのパスか参照がない、リポジトリがない、またはトークンで見えない非公開のリポジトリ。

手元のCLIはGITHUB_TOKENかGH_TOKENのトークンを使います。製品のActionsには別のトークンを渡す入力がなく、ワークフローのトークンで読める設定だけを使えます。非公開の管理リポジトリの設定は、共通のワークフロー経由で渡します。

Cloudflareの認証

メッセージ対処
Cloudflare R2 access key ID and secret must be set togetherR2のキーが片方だけ設定されています。両方設定するか、両方外してAPIトークン1つの方式にします。
Cloudflare API token is required to derive R2 credentialsAPIトークン1つの方式で、CF_API_TOKENがありません。
Cloudflare API token is required for cache invalidationキャッシュの削除が必要な実行で、CF_API_TOKENがありません。

試し実行で確かめられるのは読み取りの権限までです。キャッシュを削除する権限は、実際の実行まで確かめられません。

AWSのロールを引き受けられない

次を順に確かめます。Terraformでそのサイトのロールを作ったか、ジョブのsubがsatellite_github_subjectsの値と完全に一致するか、設定のaws.accountIdとaws.namePrefixがTerraformと合っているか。期待するロールのARNはartifact-pages registry role-arnで確かめられます。

メッセージ対処

さらに詳しい手順

内部の記録が壊れた場合の扱いなど、まれな状況の手順は、製品の復旧ガイド（英語）にあります。そこにある手順の多くは、実際の環境ではまだ試されていません。内部の記録を手で消す操作は、そのガイドの条件を満たす場合だけにしてください。
