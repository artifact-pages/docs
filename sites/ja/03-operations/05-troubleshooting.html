社内展開と運用

問題を調べ、復旧する

ほとんどの失敗は、同じ操作をもう一度実行すれば収まるように作られています。まず何が失敗したかを確かめ、必要ならロックを解いてから、元の操作をやり直します。

まず切り分ける

  1. 失敗したジョブの概要（Job Summary）で、実行されたCLIの版（CLI executed）、操作、結果、エラーを確かめます。
  2. 終了コードを見ます。2は引数や設定の誤り、1は配信先、ダウンロード、互換性の確認などの失敗です。
  3. 同じ操作を--dry-runで動かします。試し実行では読み取るだけで、ロックも取らず、何も書き込みません。

読者の画面に出る表示から調べる

読者から「開けない」と言われたときは、閲覧アプリに出ている英語の表示を聞きます。表示ごとの原因と、管理者やチームがすることは次のとおりです。

  • Site registered, but not published yet：サイトは登録されているが、配信先にサイトの一覧がない。初めての公開の前に出ます。公開したはずなのに出る場合は、配信先のデータが消えています。正しい公開元からsite sync --reconcileを実行します。
  • Site registered, but details are unavailable：サイトの概要と一覧を読み込めない。まず通信、閲覧の制限、配信先の応答を調べて、読み込み直します。データが消えたり壊れたりしているなら、正しい公開元からsite sync --reconcileを実行します。
  • This site needs to be republished：サイトのデータの形式を、いまの閲覧アプリが読めない。互換性を確かめたうえで、閲覧アプリに合うCLIでそのサイトをsite syncします（「形式が変わる更新」）。
  • This library needs to be updated：サイトの登録情報の形式を、いまの閲覧アプリが読めない。管理者が互換性と更新の順番を確かめてregistry syncし、各サイトをsite syncします。
  • Document unavailable：Artifactの本文を読み込めない。削除されたか、まだ公開されていないか、通信の問題です。公開元にあるのに配信先にないなら、site sync --reconcileで直します。
  • Page text search is not available：本文検索のデータなしで公開されたサイト。いまのCLIでsite syncすると使えるようになります。
  • Page text search needs to be republished：本文検索のデータの形式を、いまの閲覧アプリが読めない。閲覧アプリに合うCLIでsite syncします。
  • Preview unavailable：プレビューが削除されたか、保持期間が過ぎて消えた。必要なら、そのプルリクエストでプレビューを作り直します。
  • This preview needs to be republished：プレビューの形式を、いまの閲覧アプリが読めない。閲覧アプリに合うCLIでプレビューを作り直します。

ロックが残っている

同じサイトへの操作は、ロックで1つずつ順に行われます。ロックは自動では期限切れになりません。操作が途中で強制終了されるとロックが残り、次の操作は10秒待ってからtimed out waiting for site "…" lockで失敗します。

ターミナル
# ロックの状態を見る（共有のロックは --scope registry か --scope application）
$ artifact-pages lock inspect --site sre --config artifact-pages.yaml --format json
# 表示された etag を指定して解く
$ artifact-pages lock recover --site sre --observed-etag ETAG --config artifact-pages.yaml
  • 解く前に、本当に誰も動いていないかを確かめます。サイトのロックは、そのサイトの公開とプレビュー、サイトを変えるregistry sync、app deployが取ります。管理リポジトリだけでなく、各チームのジョブや手元の実行も確かめます。取った時刻だけで古いと判断しないでください。
  • lock recoverに試し実行はありません。確かめたetagと今の状態が違えば、何もせずに失敗します。
  • 解くのはロックだけです。そのあとで、止まっていた元の操作をもう一度実行します。

公開や配置が途中で止まった

公開は多数のファイルの書き込みで、途中で失敗しても自動では元に戻りません。同じ公開元と設定で、同じ操作をもう一度実行すれば、残りを書き込んで収まります。

止まった操作やり直すこと
サイトの公開同じsite sync。前回の書き込みの残りを済ませるので、公開元に変更がなくても結果がsyncedになることがあります。
登録の反映、サイトの取り下げ同じ設定でregistry sync。
閲覧アプリの配置同じapp deploy。

書き込みの残りを済ませたあと、再試行の記録を消せなかったときのメッセージはsite origin transaction recovered; remove journal: …です。配信先の内容はそろっています。同じsite syncをもう一度実行して、記録を消します。

配信先の中身がずれている

誰かが配信先のファイルを直接消したり置き換えたりすると、公開の内容とずれます。通常の公開は、公開元が前回と同じなら配信先の個々のファイルを確かめずにno-opで終わるので、このずれには気付きません。

ターミナル / チームのリポジトリ
$ artifact-pages site sync --site sre --config 'github://acme/platform-admin/artifact-pages.yaml?ref=main' --reconcile --dry-run
$ artifact-pages site sync --site sre --config 'github://acme/platform-admin/artifact-pages.yaml?ref=main' --reconcile

--reconcileは、配信先のファイルの一覧とメタデータを公開元と突き合わせ、足りないファイル、余分なファイル、メタデータの違いを直します。ファイルの中身までは読まないので、メタデータを保ったまま中身だけが壊れた場合は見つけられません。公開した内容そのものが間違っている場合は、正しいコミットを取り出して公開し直します。--refは表示用の情報を変えるだけで、公開する内容は変えません。

公開してはいけないものを公開した

秘密の値や、社外に見せてはいけないファイルを公開してしまったときは、次の順に対処します。配信先から消しても、すでに読まれた写しは取り戻せません。最初に、漏れた値を無効にします。

  1. 漏れた認証情報やトークンを失効させます。代わりを発行して、使っている場所のシークレットを入れ替えます。
  2. 公開元から取り除いて、公開し直します。正しい状態にしたコミットからsite syncを実行すると、公開元からなくなったArtifactは配信先からも削除されます。
  3. そのファイルを含むプレビューを削除します。本公開を直しても、プレビューは残ります。そのファイルを含むプレビューのグループごとにpreview removeを実行します（「プレビューだけを削除する」）。
  4. キャッシュに残った写しを確かめます。CLI 0.6以降は、Artifactとプレビューを、新しく読み込むたびに配信先へ確かめ直す設定で書きます。ただし、同じURLの写しが0.5以前の設定や独自のCDNの設定でキャッシュに残っていると、公開し直したあとも、その写しが切れるまで（以前の標準の設定では最大300秒）古い内容が返ることがあります。CLIはキャッシュの削除をしません。すぐに消す必要があれば、CloudflareのURLごとの削除やCloudFrontの無効化を手で行えます。読者のブラウザや開いたままの画面にある写しは、消せません。
  5. Gitの履歴を確かめます。今のブランチから消しても、過去のコミットには残ります。リポジトリを読める人の範囲と、履歴の扱いを確かめます。

設定を読めない、認証に失敗する

別のリポジトリの設定を読めない

github://で管理リポジトリの設定を直接読む場合、失敗するとcannot read deployment config github://…で始まるメッセージが出ます。

HTTP考えられる原因
401トークンが無効か期限切れ。
403トークンにそのリポジトリのcontents:readがない、またはAPIのレート制限。
404ファイルのパスか参照がない、リポジトリがない、またはトークンで見えない非公開のリポジトリ。

手元のCLIはGITHUB_TOKENかGH_TOKENのトークンを使います。製品のActionsには別のトークンを渡す入力がなく、ワークフローのトークンで読める設定だけを使えます。非公開の管理リポジトリの設定は、共通のワークフロー経由で渡します。

Cloudflareの認証

メッセージ対処
Cloudflare R2 access key ID and secret must be set togetherR2のキーが片方だけ設定されています。両方設定するか、両方外してAPIトークン1つの方式にします。
Cloudflare API token is required to derive R2 credentialsAPIトークン1つの方式で、CF_API_TOKENがありません。

試し実行で確かめられるのは読み取りの権限までです。書き込みの権限は、実際の実行まで確かめられません。

AWSのロールを引き受けられない

次を順に確かめます。Terraformでそのサイトのロールを作ったか、ジョブのsubがsatellite_github_subjectsの値と完全に一致するか、設定のaws.accountIdとaws.namePrefixがTerraformと合っているか。期待するロールのARNはartifact-pages registry role-arnで確かめられます。

メッセージ対処
site "…" is not registered in the deployed registry管理リポジトリの変更をregistry syncで反映します。
site "…" is registered to …; selected checkout is …公開しようとしたリポジトリかディレクトリが登録と違います。

さらに詳しい手順

内部の記録が壊れた場合の扱いなど、まれな状況の手順は、製品の復旧ガイド（英語）にあります。そこにある手順の多くは、実際の環境ではまだ試されていません。内部の記録を手で消す操作は、そのガイドの条件を満たす場合だけにしてください。
