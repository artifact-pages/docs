For admins, first time

Getting started

Install the artifact-pages command, see what the admin repository and the team repositories each do, then take one site from a directory in Git to the reader app on your own machine. The try-out needs no cloud account.

Install the CLI

One command, artifact-pages, does all the work: it deploys the reader app, registers sites, and publishes them. It is a Go program built from its released source. There is no standalone binary to download.

With mise (recommended)

mise's Go backend builds the command with go install and keeps the version you choose. -g installs it for your user, in every directory.

TERMINAL / mise
$ mise use -g go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@x.y.z
$ artifact-pages version
  • Write the version without a leading v (x.y.z), as mise ls-remote go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages lists it. A very recent release may not be listed yet, because mise holds back new releases for a minimum age, but naming its version from GitHub Releases still installs it.
  • It needs Go 1.26 or later. If you don't have Go yet, add go@1.26 to the same mise use command and mise installs both.
  • mise must be active in your shell (or its shims on your PATH) for artifact-pages to be found.

With go install

The same release without mise. Here the version is the release tag, with its v.

TERMINAL / go install
$ go install github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@vX.Y.Z

Go puts the command in its bin directory (go env GOBIN, or bin under go env GOPATH); make sure it is on your PATH. x.y.z stands for a release version; releases are listed on GitHub Releases. A Homebrew formula is planned but not available yet.

ONE VERSION

The CLI's version also picks the reader app's version. artifact-pages version shows both, and app deploy installs the app of the same release. To move the app to another release later, install that release's CLI and run app deploy again.

Two kinds of repository

A deployment has one admin repository and any number of team repositories. The admin decides which sites exist; each team publishes only its own.

  1. Admin repository

    Write the delivery target and the list of sites in artifact-pages.yaml.

  2. app deploy

    Places the reader app on the delivery target.

  3. registry register

    Writes the site registrations to the delivery target.

  4. Team repository

    Runs site publish from its own CI after a merge. acme/checkout is an illustrative example.

  5. Delivery target checks the registration

    It reads the registration stored on the delivery target, not the team's config. If they do not match, nothing is written.

  6. Read in the reader app

    The published site is read in the reader app that was placed.

ADMIN REPOSITORY · ONE PER DEPLOYMENT

Owns the deployment

Holds artifact-pages.yaml: the delivery target and the complete list of sites. Runs app deploy to install the reader app and registry register to register the sites, ideally only from reviewed changes.

TEAM REPOSITORIES · ANY NUMBER · ONE OR MORE SITES EACH

Publish their own site

Keep documents in one registered directory and run site publish for their site, usually from their own CI after merge. They need only the delivery target, never the site list; they can read the admin repository's file with a github:// locator.

Whether a repository may publish to a site is decided by the site registry on the delivery target, not by the team's config. For a try-out, one repository can play both roles, which is what the next section does.

Try it on your machine

The local provider writes everything to a directory instead of cloud storage, so the whole flow runs without an account. Besides the CLI you need Git, network access to download the reader app from GitHub Releases, and Python 3 (or any static file server) to view the result.

  1. Prepare a repository

    Use a Git checkout whose origin remote is on GitHub, with at least one commit and a directory that holds at least one .html or .md page. Publishing reads dates from Git history, so it fails in a repository with no commits; the pages themselves don't need to be committed. The examples use the illustrative acme/checkout and its docs/artifacts; use your own repository's owner/repo and directory instead.

    TERMINAL / acme/checkout
    $ mkdir -p docs/artifacts
$ printf '# Payment flow design\n\nHow a card payment moves through checkout.\n' > docs/artifacts/payment-flow.md
# Only if the repository has no commits yet
$ git add -A && git commit -m "Add a first page"

  2. Write artifact-pages.yaml

    At the repository root, name the local target and register one site. repository must match the checkout's origin as owner/repo, and sourcePath is the directory, relative to the root. Add .local/ to .gitignore: everything under it is generated.

    artifact-pages.yaml / acme/checkout
    schemaVersion: 1
provider: local
local:
  root: .local/storage
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

  3. Deploy the reader app

    Downloads the reader app of the CLI's release, verifies it, and writes index.html and assets/ into .local/storage. Like the other commands here, it takes --dry-run to show the plan without writing.

    TERMINAL / acme/checkout
    $ artifact-pages app deploy --config artifact-pages.yaml --dry-run
$ artifact-pages app deploy --config artifact-pages.yaml

  4. Register the site

    Writes the site registry from the sites mapping. The site now exists, with no pages yet.

    TERMINAL / acme/checkout
    $ artifact-pages registry register --config artifact-pages.yaml --dry-run
$ artifact-pages registry register --config artifact-pages.yaml

  5. Publish

    Checks the repository and directory against the registration, then copies the pages and builds the site's index. --fulltext adds the data for page text search. Run the same command again and it reports UP TO DATE.

    TERMINAL / acme/checkout
    $ artifact-pages site publish --site checkout --source docs/artifacts --config artifact-pages.yaml --fulltext --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts --config artifact-pages.yaml --fulltext

  6. Open the reader

    Serve the directory and open http://localhost:8000/. Choose a site lists Payments / Checkout; open it, pick the page, and try page text search with ⌘⇧F / Ctrl ⇧ F.

    TERMINAL / acme/checkout
    $ python3 -m http.server 8000 --directory .local/storage
CHECK

Start from http://localhost:8000/ and move around inside the app. This simple server only serves files, so reloading an address such as /checkout/payment-flow.md returns 404 here. A delivery target set up for real use sends those addresses to the reader app.

Pass --fulltext on every publish. A publish without it removes the site's search data.

To change the site, edit or remove files in the directory and run the same site publish. It uploads what changed and removes what is gone. To start over, delete .local/storage.

Moving to a real delivery target

The commands stay the same. What changes is where they write and who runs them.

  • Set up storage and a CDN in the provider itself: S3 and CloudFront on AWS, or R2 and the Cloudflare cache. Artifact Pages doesn't create them. Then switch provider and its block in the admin repository's file; see delivery targets.
  • From the admin repository, run app deploy and registry register with admin credentials taken from the environment, never written in the file (credentials).
  • From each team repository, publish after merge from CI with credentials that can write only that site. Publishing has a GitHub Actions workflow you can start from.
  • Before anyone publishes, read Access and trust: published HTML runs as code, and limiting who can read belongs at the delivery edge.
