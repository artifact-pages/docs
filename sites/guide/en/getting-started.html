For admins, first time

Getting started

Install the artifact-pages command, see what the admin and team repositories each do, then publish a first site and read it in the reader app, using Cloudflare as the delivery target.

Install the CLI

One command, artifact-pages, does all the work: it deploys the reader app, registers sites, and publishes them. It is a Go program built from its released source. There is no standalone binary to download.

With mise (recommended)

mise's Go backend builds the command with go install and keeps the version you choose. -g installs it for your user, in every directory.

TERMINAL / mise
$ mise use -g go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@x.y.z
$ artifact-pages version
  • Write the version without a leading v (x.y.z), as mise ls-remote go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages lists it. A very recent release may not be listed yet, because mise holds back new releases for a minimum age, but naming its version from GitHub Releases still installs it.
  • It needs Go 1.26 or later. If you don't have Go yet, add go@1.26 to the same mise use command and mise installs both.
  • mise must be active in your shell (or its shims on your PATH) for artifact-pages to be found.

With go install

The same release without mise. Here the version is the release tag, with its v.

TERMINAL / go install
$ go install github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@vX.Y.Z

Go puts the command in its bin directory (go env GOBIN, or bin under go env GOPATH); make sure it is on your PATH. x.y.z stands for a release version; releases are listed on GitHub Releases. A Homebrew formula is planned but not available yet.

VERSIONS

The config picks the reader app and the CLI that runs. web.version in artifact-pages.yaml names the reader app release that app deploy installs, and the optional cli.version names the CLI. The two are released separately; Pinning and upgrading versions covers how to pin and upgrade them.

Two kinds of repository

A deployment has one admin repository and any number of team (satellite) repositories. A team that wants a new site opens a pull request against the admin repository; the admin approves and merges it and applies it to the deployment. Each team publishes only its own registered site.

The admin repository holds the delivery target and the complete list of sites. From approved changes, the admin places the reader app and registers the sites. A team repository holds only its documents and one workflow: no config file. It reads the admin repository's artifact-pages.yaml through a github:// locator. Whether a repository may publish to a site is decided by the site registry on the delivery target, not by the team's config.

Start with Cloudflare

This walkthrough uses Cloudflare as the delivery target and ends with a first site you can read. The admin repository acme/platform-admin and the team repository acme/checkout are illustrative. On AWS the flow and commands are the same; only steps 1 and 2 differ (Other delivery targets).

  1. Set up the delivery target

    Create one private R2 bucket and connect it to the hostname readers will use (docs.example.com in the examples). Also configure routing to the reader app, blocking of /_control/, cache rules and preview retention. Artifact Pages commands do not create these; set them up with Terraform or similar. The product repository has Terraform modules for this. For the admin, also prepare an R2 access key and secret and an API token that can purge the cache.

    For the detailed steps, see Cloudflare deployment in the product repository.

  2. Write artifact-pages.yaml in the admin repository

    Name cloudflare as the delivery target, name the reader app release in web.version (x.y.z stands for a release version), and list the sites under sites. repository is the team repository's owner/repo, and sourcePath is the directory relative to its root. If the bucket is not named artifact-pages, add bucket (see cloudflare).

    artifact-pages.yaml / acme/platform-admin
    schemaVersion: 1
web:
  version: x.y.z   # the reader app release step 3 installs
provider: cloudflare
cloudflare:
  accountId: "<32-character account ID>"
  zoneId: "<32-character zone ID>"
  publicBaseURL: https://docs.example.com
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

  3. Deploy the reader app

    Run this in the admin repository with the admin credentials in environment variables. It downloads the reader app release named by web.version, verifies it, and writes it to the bucket. Like the other commands here, it takes --dry-run to show the plan without writing.

    Terminal / acme/platform-admin
    # Pass values through the environment, never in a file
$ export CF_R2_ACCESS_KEY_ID=… CF_R2_SECRET_ACCESS_KEY=… CF_API_TOKEN=…
$ artifact-pages app deploy --config artifact-pages.yaml --dry-run
$ artifact-pages app deploy --config artifact-pages.yaml

  4. Register the site

    Writes the site registry from the sites mapping to the delivery target. The site now exists, with no pages yet.

    Terminal / acme/platform-admin
    $ artifact-pages registry register --config artifact-pages.yaml --dry-run
$ artifact-pages registry register --config artifact-pages.yaml

  5. Publish from the team repository

    Put at least one .html or .md page in docs/artifacts of acme/checkout. Publishing reads dates from Git history, so it fails in a repository with no commits. The repository has no config file; pass a github:// locator for the admin repository's file to --config. You can pin it to one commit with ?ref=. The CLI reads the registry on the delivery target, checks the repository and directory against it, then copies the pages and builds the site's index. It also builds the data for page text search every time.

    Terminal / acme/checkout
    $ artifact-pages site publish --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml

    It needs the R2 access key and secret, and the API token for runs that change the site. The first run can be from your machine; after that, run it from CI after merges. Publishing has a GitHub Actions workflow you can start from. If the admin repository is private, it is read with GITHUB_TOKEN or GH_TOKEN.

  6. Open it in a browser

    Open https://docs.example.com/. Choose a site lists Payments / Checkout; open it, pick the page, and try page text search with ⌘⇧F / Ctrl ⇧ F. Reloading an address such as /checkout/payment-flow.md works too: the routing set up in step 1 hands it to the reader app.

To change the site, edit or delete files in the directory and run the same site publish. It uploads changed files and removes the ones that are gone.

Other delivery targets

On every delivery target the commands and steps 3 to 6 are the same. What changes is how the delivery target is set up and the provider settings in artifact-pages.yaml.

  • AWS: set up S3 and CloudFront and use provider: aws (see aws). Credentials follow the standard AWS lookup; in CI, assume a role with OIDC.
  • Before anyone publishes, read Access and trust. Published HTML runs as code, and restricting who can read belongs at the delivery edge.
Try it on your machine (local provider)

The local provider writes to a local directory instead of cloud storage, so you can try the flow without an account, with one repository playing both roles. Set repository to the checkout's origin as owner/repo. Everything under .local/ is generated; add it to .gitignore.

artifact-pages.yaml / acme/checkout
schemaVersion: 1
web:
  version: x.y.z   # the reader app release step 3 installs
provider: local
local:
  root: .local/storage
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

Steps 3 to 5 use the same commands, with no credentials and --config artifact-pages.yaml. To serve the written directory you need a server that hands addresses such as /checkout/payment-flow.md to the reader app and never serves /_control/. With nginx:

nginx.conf / acme/checkout
server {
  listen 80;
  root /usr/share/nginx/html;

  location = /_control { return 404; }
  location ^~ /_control/ { return 404; }
  location ^~ /_indexes/ { try_files $uri =404; }
  location ^~ /_artifacts/ { try_files $uri =404; }
  location ^~ /_previews/ { try_files $uri =404; }
  location ^~ /assets/ { try_files $uri =404; }
  location / { try_files $uri $uri/ /index.html; }
}
compose.yaml / acme/checkout
services:
  web:
    image: nginx:1.29-alpine
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./.local/storage:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
Terminal / acme/checkout
$ docker compose up -d

Open http://localhost:8080/. This is a minimal configuration for trying things out; the product repository's docker/nginx/default.conf adds per-site CSP and cache headers. To start over, delete .local/storage.
