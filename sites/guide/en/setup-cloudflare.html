Setting up Cloudflare

This is the detailed version of step 1 in Getting started: preparing a Cloudflare R2 bucket and hostname as the delivery target. It covers what to prepare, what to decide, and what to check before the first apply. Every Terraform input is documented in the product's module README, so this page points there instead of repeating it.

What you get

The product's Cloudflare Terraform module creates the delivery target that the CLI then publishes to:

  • One private R2 bucket. It holds the reader app, the site registry, the published pages, and the previews.
  • The hostname. It connects the bucket to the custom domain readers use and routes unmatched paths, including /_control/*, to the reader app instead of to stored objects.
  • Cache and response rules. The cache respects the origin's cache headers, and published HTML and previews receive the same Content Security Policy.
  • Unchanged delivery. For this hostname only, a Configuration Rule turns off the Cloudflare features that rewrite or inject into response bodies, such as email obfuscation, Rocket Loader, and Polish, so pages reach readers exactly as published.
  • Preview expiration. Previews are removed by an R2 lifecycle rule after the number of days you choose.
  • r2.dev kept disabled. The bucket's alternate public address is managed and kept off, so turning it on in the dashboard shows up as a difference in the plan.

The module does not deploy the reader app, register sites, create the CLI's credentials, or set who may read. Those are separate steps: app deploy and registry sync in Getting started, the credentials below, and Access and trust.

AWS

Setup for AWS (S3 and CloudFront) is not covered in this guide yet. The AWS settings of the config file are described in Configuration.

What you need first

  • A Cloudflare account with R2 enabled. You need its 32-character account ID.
  • A zone for the hostname. The DNS zone that will contain the hostname readers use (docs.example.com in the examples) must already exist in that account. You need its 32-character zone ID.
  • Terraform and the Cloudflare provider. The module supports Terraform >= 1.5.0, < 2.0.0 and Cloudflare provider >= 5.24.0, < 6.0.0.
  • A decision on preview retention. preview_retention_days is a whole number of days from 1 to 36500. It is required, and it lives only in Terraform: the CLI config has no retention value.

Call the module

Write a small Terraform root module in the admin repository, or next to it, that calls the Cloudflare module. This is the smallest form; bucket_name is optional and defaults to artifact-pages. The source below pins a release of the module's package repository. Publication to the Terraform Registry is planned, and this page will move to the Registry source then.

main.tf / acme/platform-admin
terraform {
  required_version = ">= 1.5.0, < 2.0.0"

  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = ">= 5.24.0, < 6.0.0"
    }
  }
}

module "artifact_pages" {
  source = "git::https://github.com/artifact-pages/terraform-cloudflare-artifact-pages.git?ref=v0.1.0"

  account_id             = var.cloudflare_account_id
  zone_id                = var.cloudflare_zone_id
  public_hostname        = var.public_hostname
  preview_retention_days = var.preview_retention_days
  # bucket_name = "artifact-pages"   # optional
}

provider "cloudflare" {}   # reads CLOUDFLARE_API_TOKEN

output "artifact_pages_deployment_config_yaml" {
  value = module.artifact_pages.artifact_pages_deployment_config_yaml
}

The variables are your account ID, zone ID, hostname without a scheme, port, or path, and retention days. Supply them in an untracked variable file. The full list of inputs, with defaults and rules, is the Inputs table in the module's README (terraform-cloudflare-artifact-pages).

Review the plan before you apply

Run terraform plan first and read it. The module takes ownership of whole sets of settings, so a zone or bucket that already has some of them needs attention before the first apply. The module README's Resource ownership and apply review section has the exact steps and import addresses.

  • Existing zone rules. The module owns the complete transform, cache, response-header, and configuration rulesets of the zone. If any of them already exists, first set the matching *_ruleset_name input to its current name (ruleset names cannot be changed, so a different name plans a replacement), then import it, then pass all its existing rules through the matching existing_*_rules input in the same order. Otherwise the first apply fails or replaces them. The dashboard creates the configuration ruleset with its first Configuration Rule, so check that one too. When you set waf_custom_rules, the same applies to the custom firewall ruleset (waf_custom_rules.ruleset_name and existing_rules). It has prevent_destroy.
  • The bucket name. The default artifact-pages is not reserved. If a bucket with the chosen name exists in the account, creation fails. The module always creates its bucket; to use an existing one, see "Existing-bucket use" in the README.
  • The custom domain. The provider cannot import an existing R2 custom domain. If the hostname is already connected, set connect_custom_domain = false and check separately that the connection is enabled with the TLS version you want.
  • Lifecycle rules. The module owns the bucket's complete lifecycle rule set. Pass every other rule you want to keep through additional_lifecycle_rules. The provider cannot import or destroy this resource, so removing it from Terraform leaves the rules in place.
  • r2.dev stays disabled. If you enable it in the dashboard, it bypasses the hostname's routing and could expose private /_control/* objects, and the next plan shows the difference. Leave it off.
  • The bucket is not force-destroyed. Empty or move the contents deliberately before you destroy it. Removing the module is neither a backup nor a rollback of what the CLI published.
  • Cost. R2 storage and requests, custom domains, and rules can be billable, and rules have plan limits. The module does not estimate your account's charges, so check pricing and limits for your plan.
VIEWERS

The module does not decide who can read. Restrict the hostname with Cloudflare Access or another edge policy yourself. The optional waf_custom_rules input can manage rules for the hostname, such as an IP allowlist, but it does not configure authentication. See Access and trust.

Fill the CLI config from the outputs

After the apply, the module's artifact_pages_deployment_config_yaml output is ready-to-copy YAML for the delivery target. It holds only non-secret identifiers and the effective bucket name. Credential variable names are left out when they have their default values (CF_R2_ACCESS_KEY_ID, CF_R2_SECRET_ACCESS_KEY, CF_API_TOKEN), and written out when you renamed them.

Terminal / acme/platform-admin
$ terraform output -raw artifact_pages_deployment_config_yaml
output / illustrative values
"cloudflare":
  "accountId": "<32-character account ID>"
  "bucket": "artifact-pages"
  "publicBaseURL": "https://docs.example.com"
  "zoneId": "<32-character zone ID>"
"provider": "cloudflare"
"schemaVersion": 1

The keys come out quoted and in alphabetical order. That is valid YAML; tidy it when you copy. If registry_reader is set in the module call, its environment variable names are written too.

Copy these keys into artifact-pages.yaml in the admin repository, then add web.version and the sites mapping, as in step 2 of Getting started. The meaning of each key is in Configuration. Put the credential values in the environment of the admin job and the team jobs, never in the file.

docs.example.com and the placeholders are illustrative. The generated values are public identifiers, not secrets, so the file can be committed to the admin repository.
