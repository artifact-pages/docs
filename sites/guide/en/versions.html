Pinning and upgrading versions

The admin config names the CLI and the reader app a deployment runs. Change them in one place, check the change in a pull request, and every site follows on its next run. This page shows how to pin, upgrade, and handle a breaking change.

What has a version

Three kinds of component are released independently, each in its own tag series. A release of one does not release the others.

ComponentTagWhat it isWho chooses the version
CLIvX.Y.ZThe artifact-pages command, which publishes sites and deploys the app.The config, cli.version
Reader app (web)web/vX.Y.ZThe bundle that app deploy installs for readers.The config, web.version
Each GitHub Actionpublish-action/vX.Y.Z, preview-action/…, registry-action/…, app-deploy-action/…A thin wrapper that runs the CLI in a workflow. Your workflow references it as artifact-pages/publish-action@vX.Y.Z.Your workflow file

CLI and reader app releases are listed on the GitHub Releases of the product repository. Each Action is released in its own repository, so its tags are plain vX.Y.Z there. x.y.z stands for a release version throughout this page.

Whether two versions work together is never decided from their numbers. The CLI and the app each carry the data formats they write and read, storage records what was actually written and deployed, and the commands compare those. While the product is 0.x no compatibility is promised, so these checks are the only guard.

Pin the versions in the config

Add cli and web to the admin repository's artifact-pages.yaml:

artifact-pages.yaml / acme/platform-admin
schemaVersion: 1
cli:
  version: x.y.z   # the CLI every run uses
web:
  version: x.y.z   # the reader app that app deploy installs
provider: cloudflare
# ... provider settings and sites as usual
  • Exact versions only. Write MAJOR.MINOR.PATCH. A leading v, a range, latest, and pre-release or build suffixes are rejected with exit code 2.
  • Set each key in one layer only. If you stack layers, cli and web may come from at most one of them, even when two layers name the same value. One layer may set both. The admin config is the natural place.
  • cli.version selects the CLI that runs. The installed artifact-pages reads the config first and, if it names another release, downloads that release, checks its checksum, and runs it with the same arguments. This applies to app, site, registry, preview, lock, and config check. Without cli.version, the installed CLI runs itself.
  • web.version selects the reader app. app deploy downloads release web/vX.Y.Z of the product repository, verifies it, and installs it. Downloads come only from official releases.
  • A config that sets either key is pinned. That turns on the compatibility checks described below.

How sites follow

Site repositories do not choose the CLI. On its next site sync (named site publish in the other guide pages, which are still to be revised) or preview publish, a site's workflow reads the admin config, which it already points to with a github:// locator, and runs the CLI that config names. Raising cli.version once therefore moves every site, within each Action's supported range (see below), with no pull request in the site repositories.

  • Writers check the deployed app. registry sync, site sync, and preview publish read what the deployed reader app can read and stop before writing if it cannot read a format this CLI writes. A CLI newer than the deployed app therefore cannot publish pages the app cannot show, unless you accept that explicitly with registry sync --accept-breaking (see below). If no app has been deployed yet, they check against the formats listed in the manifest of the web.version release. A legacy config is not checked.
  • Previews cannot change the CLI. The preview Action resolves the CLI only after its trust preflight, and reads config layers owned by the repository from the trusted base commit, so a pull request cannot change which CLI runs by editing them. Explicit external operator files and remote locators keep their own authority.

What the Action version means

An Action's version no longer decides which CLI runs. Each Action release records a bootstrap CLI, the release it installs first, and a supported range of CLI versions (cliRange, for example >=0.1.0 <0.2.0). The bootstrap reads the config and switches to the CLI the config names.

  • Keep pinning Actions to an exact tag (or a full commit SHA, which fixes the same data), as in Publishing. The pin fixes the bootstrap and the range.
  • Upgrade an Action only when you need to. That is when the CLI you want lies outside its range. The run then fails with exit code 2, naming the version and the range, before anything is downloaded. Move to an Action release with a wider range first, then raise cli.version.
  • Each run reports what ran. The Job Summary shows CLI executed with the version that actually ran. If the CLI could not be installed, it reads CLI executed: none (installation failed).

Upgrade

For a release that keeps the data formats readable, the upgrade is a change to the admin config:

  1. Bump the version in a pull request

    Change cli.version, web.version, or both in the admin repository. Keeping them current is your repository's job; an update bot in your repository can open these pull requests.

  2. Run config check in CI

    It runs under the CLI the config names. It fails, writing nothing, unless the new app reads every format that CLI writes and every format recorded in storage for the registry and each site. Sites that need a republish are listed. It needs web.version (exit code 2 without it).

    CI / acme/platform-admin
    $ artifact-pages config check --config artifact-pages.yaml

  3. On merge, apply

    Run registry sync, then app deploy when web.version changed. Use --dry-run to see the plan first.

    CI / acme/platform-admin
    $ artifact-pages registry sync --config artifact-pages.yaml
$ artifact-pages app deploy --config artifact-pages.yaml

  4. Sites follow

    Each site uses the new CLI on its next sync or preview. Nothing is needed in the site repositories, unless the new CLI is outside their Actions' range (see above).

app deploy also checks the other direction before it writes: the app it installs must read every format recorded in storage for the registry and for every registered site. If a record is missing, incomplete, or names a format the app cannot read, the command fails and lists each registry or site that needs a republish.

A breaking format change

Some releases change a data format that the deployed app cannot read. The normal checks refuse that on purpose, and config check is expected to fail for it, so this path skips config check. The three steps below, with their own checks, replace it. Accept the change explicitly, in this order:

  1. registry sync --accept-breaking

    Lets the new CLI write the registry although the deployed app cannot read it yet.

  2. app deploy --accept-breaking

    Installs the new app although stored sites and the registry are not yet in a format it reads, including records that are unknown or incomplete.

  3. Republish every site

    Run site sync for each site with the new CLI.

READERS SEE IT

Until a site is republished, readers see "needs to be republished" for it. Plan the three steps together and republish promptly.

--accept-breaking exists only on registry sync and app deploy. It never overrides a version record with an unsupported schemaVersion, and registry sync never overrides an incomplete record. site sync and preview publish have no such flag.

Run another CLI once

To try a release in one site, or in an emergency, override the config's cli.version for a single run. Pick one of these:

WhereForm
CLI flag--cli-version x.y.z, before or after the command name
Environment variableARTIFACT_PAGES_CLI_VERSION=x.y.z
Action inputcli-version: x.y.z
  • Precedence: the flag, then the environment variable, then the Action input, then the config. The value must be an exact release version (exit code 2 otherwise).
  • An override never skips a check. It only replaces which CLI runs; that CLI reads the same config and storage and runs the same compatibility checks.
  • It must lie within the Action's range. Otherwise the run fails with exit code 2 before downloading.
  • It is visible. The Job Summary adds CLI override with the source and, when the config names a version, that version.

A deployment without pins

A config with neither cli nor web is legacy. It keeps the unpinned flow as long as storage has no app version record: no CLI switching, and app deploy without web.version installs the app of the CLI's own release, without format checks. That path resolves only for releases made before the series split, because later CLI releases carry no app bundle. Once an app version record exists in storage, the checks apply whatever the config says.

  • Set web.version when you adopt pinning. app deploy with cli.version but neither web.version nor --archive exits with code 2, and so does config check without web.version.
  • Update the Actions and CLIs first. An older CLI rejects the unknown cli and web keys, so move to releases that understand them before the config adds the keys.
  • Existing sites are unknown until they are republished. Data written before version records existed has no record, so app deploy and config check fail and list those sites. A republish creates the record. With web.version set, republish first, then deploy: run registry sync, then site sync for every site (while no app record exists, writers check against the manifest of the web.version release), then app deploy. Alternatively, follow the breaking order with --accept-breaking.

acme/platform-admin is an illustrative admin repository. Replace x.y.z and vX.Y.Z with real release versions.
