For publishing teams

Publishing

Each team publishes its own site from one directory in its Git repository. This page covers what goes in that directory, the site sync command, running it from CI, and previews.

BEFORE YOU START

Before you start, you need two things: the artifact-pages command, and a site that an admin has registered for your repository and directory. Ask the admin for the site ID and the address of the admin repository's config.

A satellite repository is just documents plus one workflow. It holds the published directory and a CI workflow, with no config file, no build step, and no sync step: it points at the admin repository's artifact-pages.yaml with a github:// locator. The commands below leave out --config for brevity; pass it, or set ARTIFACT_PAGES_CONFIG to the locator, such as github://acme/platform-admin/artifact-pages.yaml.

To install the CLI, see Getting started. The examples below use the illustrative checkout site, published from docs/artifacts in acme/checkout.

What to publish

A site comes from one directory in one repository: the sourcePath that the admin registered. Everything in that directory is published as it is, so it must already be ready to serve. Publishing does not run a site generator, expand templates, bundle CSS or JavaScript, or rewrite links. If you use a generator, publish its output directory.

  • Every .html, .htm, and .md file is a page, in any folder, including index.html and files in folders such as _includes/. Keep templates and partials outside the directory.
  • index.html is an ordinary page. /checkout opens the site's home page, not index.html.
  • Other files are published but not listed: CSS, JavaScript, images, fonts, JSON, and so on. Pages load them with relative links such as img/flow.svg or ../assets/report.css. A root-relative link such as /assets/report.css points outside the site and breaks.
  • Titles come from an HTML page's <title> or a Markdown page's first # heading. Without one, the filename is used: payment-flow.html becomes “Payment Flow”.
  • Dates and committers come from Git history. A file changed or added in the working tree uses its modification time when that is newer than its commit date. Files Git ignores, such as generated output, are still published; they take the newest modification time among the files in the page's directory and its subdirectories, and show no committer. In CI with a shallow checkout the dates are the same in normal use; see Shallow checkouts and dates.
  • Symbolic links make publishing fail. The .git folder is never published.
CHECK

Every file in the directory can be read once published, even if no page links to it. Keep secrets, private notes, and drafts out of the directory. HTML runs as published, so publish only HTML you trust; see Access and trust.

Publish with site sync

Run the command in a checkout of the registered repository. Check the plan with --dry-run first, then publish.

TERMINAL / acme/checkout
# See what would change (writes nothing)
$ artifact-pages site sync --site checkout --source docs/artifacts --dry-run
# Publish
$ artifact-pages site sync --site checkout --source docs/artifacts
  1. Build

    Reads the directory and builds the site's page index: titles, headings, dates.

  2. Check

    Reads the site registry from the delivery target. The repository and directory must match the site's registration, or nothing is written.

  3. Sync

    Uploads new and changed files, replaces the index, then removes files that are no longer in the directory.

  4. Refresh

    Asks the CDN to refresh the URLs that changed.

The repository is identified from the checkout's Git remote as owner/repo. Publishing changes only your site: never another site, the site registry, or the reader app. Only one publish runs for a site at a time.

OptionWhat it does
--site IDRequiredThe registered site ID. It is never inferred from the repository.
--source DIROptionalThe directory to publish. Its path from the repository root must equal the registered sourcePath. Defaults to that registered path.
--config LOCATOROptionalThe deployment config that names the delivery target. A satellite repository passes the admin repository's github:// locator; see Remote config. Configuration explains how it is chosen when omitted.
--ref REFOptionalOverrides only the source.ref metadata recorded in the site's index. It does not select a checkout or change the published files. An empty value keeps the branch or commit inferred from the checkout.
--reconcileOptionalChecks the complete inventory on the delivery target by object metadata, without downloading every file body.
--dry-runOptionalShow the changes without writing, deleting, or requesting a cache refresh.
--format text|jsonOptionaljson returns the complete change list, for CI.

Text output starts with the result (DRY RUN, SYNCED, or UP TO DATE) and lists created, updated, and removed paths, up to 12 per group. The exit code is 0 for a plan, a publish, or no change; 2 for invalid options or config; and 1 when the sync fails.

Page text search

site sync builds and publishes the data for the reader's page text search on every run; there is no option to leave it out. Readers of the site get the search field in the sidebar and ⌘⇧F. A site published by an earlier version gets page text search when it is published again.

What is searched: an HTML page's title and its static text, and a Markdown page's title and rendered text, including code blocks. Text that scripts create, image alt text, and paths are not searched. Text hidden only with CSS is still searched. To leave out navigation or other repeated text, mark its element with hidden, aria-hidden="true", or data-search-ignore.

When readers see the change

  • Not all at once. Files are uploaded first, the index next, and old files are removed last. While a publish runs, a reader may briefly see a mix of old and new.
  • Caches. The delivery CDN may keep a site's index for up to 60 seconds and pages for up to 300 seconds. Publishing asks it to refresh the changed URLs.
  • Open readers. Someone who already has the site open sees new pages in the sidebar after reloading.
  • Failures. Fix the cause and run the same command again; it finishes the remaining changes. There is no rollback: to undo, publish the earlier content again.

Run it from CI

The usual setup runs the same command in CI: a dry run on pull requests, and a publish after merge. Which branch may publish is your workflow's decision; the site registry has no branch setting.

  1. On a pull request: plan

    Run with --dry-run and read-only credentials. The JSON result lists exactly what would change.

    CI / PULL REQUEST
    $ artifact-pages site sync --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --dry-run --format json

  2. After merge: publish

    Run the same command without --dry-run, using credentials that can write only this site.

    CI / DEFAULT BRANCH
    $ artifact-pages site sync --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --format json
  • Credentials stay in the CI secret store, never in the config file. A publishing job needs to read the site registry, to read the deployed-web record (_control/versions/app.json), to read, write, and delete only this site's files and previews and its own control prefix (_control/sites/<site>/: the lock, cache-retry journal, and sync state), and to request a CDN cache refresh. See Configuration.
  • No config file in the repository. The job points --config at the admin repository's file with a github:// locator, optionally pinned with ?ref=<full commit SHA>; see remote config. Eligibility is still checked against the registry on the delivery target, not against the config.

With GitHub Actions

The publish Action, artifact-pages/publish-action, runs the same publish. It installs a bootstrap CLI and then runs the CLI release that the admin config names (see Pinning and upgrading versions), and takes the options as inputs: site (required), source, ref (the --ref metadata), config, and dry-run, plus cli-version, github-token, publish-on, summary, checkout, and fetch-depth (described below). This workflow plans on pull requests and publishes after merge to main:

.github/workflows/publish-docs.yml / acme/checkout
name: Publish docs

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: publish-docs-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  publish:
    runs-on: ubuntu-24.04
    # plan: read-only credentials; production: write access to this site only
    environment: ${{ github.event_name == 'pull_request' && 'plan' || 'production' }}
    steps:
      # No actions/checkout step: the Action checks out the repository itself (shallow)
      - uses: artifact-pages/publish-action@vX.Y.Z
        with:
          site: checkout
          source: docs/artifacts
          config: github://acme/platform-admin/artifact-pages.yaml   # the admin repository's config; no file in this repository
          dry-run: ${{ github.event_name == 'pull_request' }}
        env:
          CF_R2_ACCESS_KEY_ID: ${{ secrets.CF_R2_ACCESS_KEY_ID }}
          CF_R2_SECRET_ACCESS_KEY: ${{ secrets.CF_R2_SECRET_ACCESS_KEY }}
          CF_API_TOKEN: ${{ secrets.CF_API_TOKEN }}
  • The Action checks out the repository for you. By default (checkout: auto) it runs actions/checkout with fetch-depth: 1 and without persisted credentials, unless the workspace already is a checkout. Add your own checkout step only if an earlier step needs the files; the Action then leaves it alone. permissions: contents: read is enough. See Shallow checkouts and dates for what a shallow checkout means for dates.
  • Reference an exact release tag, such as @vX.Y.Z; each Action is released in its own repository (for example artifact-pages/publish-action) with its own tags. While versions are 0.x there is no moving tag such as @v0. For the strictest pin, use the release's full commit SHA and keep the tag as a comment: artifact-pages/publish-action@<full commit SHA> # vX.Y.Z. The Action's version does not choose the CLI that runs; the admin config does, and the Action only fixes the bootstrap CLI and the range of CLI versions it supports. To run a different CLI for one run, use the cli-version input. Pinning and upgrading versions has the details.
  • Two environments hold different secrets. plan and production are illustrative names: give plan read-only credentials (pull requests from forks get no secrets, so the plan fails there by design) and production credentials that can write only this site, and limit production to main in its settings. Private repositories on GitHub Free cannot use environment secrets; see Configuration. The variable names are the Cloudflare defaults; on AWS, assume a role through OIDC instead (add id-token: write to permissions).
  • One publish at a time. Only one publish can hold the site's lock, so the concurrency group runs one publish at a time (a newer push replaces a waiting one).
  • Pinning the config is optional. Without ?ref=, the admin repository's default branch is resolved to one commit for the whole run. Append ?ref=<full commit SHA> to the locator to pin a commit.
  • A private admin repository is read with this workflow's token by default, which cannot read another private repository. Pass a read-only token for the admin repository through the github-token input; Configuration shows how to mint one with a GitHub App.
  • Results are available as outputs, such as outcome (planned, synced, no-op, or failed), changes, preview-changes, and result, along with operation, site, exit-code, and error. With summary: true (the default) the Action also writes a Job Summary, even when the run fails.
  • Make a run a dry run by event. publish-on takes a newline-separated list of event or event:ref entries, such as push:refs/heads/main. A run that matches none of them becomes a dry run, and an explicit dry-run: true always wins. Empty means no condition. checkout is described above and fetch-depth under Shallow checkouts and dates below; github-token is for a private admin repository (above) and cli-version for running another CLI once.
  • Other Actions are separate repositories with their own tags: artifact-pages/registry-action for the registry, artifact-pages/app-deploy-action for app deploy, and artifact-pages/preview-action for previews.

acme/checkout and acme/platform-admin are illustrative. Replace vX.Y.Z and <full commit SHA> with real values.

Shallow checkouts and dates

The workflow above does a shallow checkout: only the latest commit. When the CLI needs older history, it fetches it from origin by itself, using this workflow's token. A dry run deepens in the same way, so the plan equals the real publish.

  • Dates and committers match a full clone in normal use. A document whose content has not changed since the last publish keeps the date and committer already in the published index. Its content is the document plus the files whose commits count toward its date, such as the CSS and images it loads, compared by checksum. So the date a page shows means when its content last changed, except in the case below. A document whose content did change gets its date from the newest commit in the history the checkout holds, and the CLI fetches more history until that date can be trusted.
  • The one difference: commits that change no bytes. A commit that touches a document or its files without changing their bytes, and that lies beyond the history the CLI fetched, is not seen. Examples are a revert back to the published content, a touch, and a history rewrite that preserves content. The page keeps its published date and committer. A full clone would show the date and author of that commit.
  • Changing the depth can change dates. Dates always come from the history the checkout can see. The first publish of a site, or a publish when the previous publish's state is missing or cannot be verified, fetches the full history first and computes dates from it. Moving between a shallow and a full checkout changes dates only where commits that change no bytes exist.
  • Previews are not affected. The CLI deepens until the merge base with the default branch is exact, so the changed pages are the same as with a full clone.

If commits that change no bytes must show up in the dates, check out the full history. Set fetch-depth on the Action:

.github/workflows/publish-docs.yml / FULL HISTORY
      - uses: artifact-pages/publish-action@vX.Y.Z
        with:
          fetch-depth: 0   # full history; slower checkout on large repositories
          # ...site, source, config, dry-run as above

If the fetch fails, for example because the token cannot read the repository, the publish stops with a message that points to fetch-depth: 0 or to a token that can read the repository. It never falls back to wrong dates.

Previews

A preview lets reviewers read changed pages before merge, without changing the published site. It is a separate command, preview publish.

TERMINAL / acme/checkout (pull request #42)
$ artifact-pages preview publish --site checkout --source docs/artifacts --base-url https://docs.example.com --pull-request 42 --dry-run
$ artifact-pages preview publish --site checkout --source docs/artifacts --base-url https://docs.example.com --pull-request 42

--base-url is the reader's address, used to build the returned links; https://docs.example.com is illustrative. --site, --source, and --base-url are required.

WHAT IS INCLUDED

HTML and Markdown pages added or changed on the head (--head, default HEAD) since it branched from the default branch (--default-ref, default origin/HEAD), plus the files they load.

Links to unchanged pages open their published version. Deleted pages have no preview. Add --include PATH for resources whose names scripts build at run time.

WHERE READERS FIND IT

Each page gets a URL like /checkout/_previews/<head SHA>/design/payment-flow.html. The site home's View previews link and the palette's Open previews command list them.

Previews do not appear in Browse, search, or Recently updated.

  • Pull requests. With --pull-request (a number or the PR's URL), the preview is grouped under that PR and shows a link back to it. The PR must come from the registered repository itself; pull requests from forks are refused. Without the option, the preview is a manual one with no PR link.
  • Posting links. The command returns the preview URLs (use --format json). Whether to comment them on the PR is up to your workflow.
  • Lifetime. A newer preview for the same PR replaces the older one in the list, but the older URLs keep working until the delivery target's retention rule deletes them. The admin sets that rule in the provider, not in Artifact Pages.
  • Trust. Preview HTML runs exactly like published HTML, before review is finished. Publish previews only from branches you trust.

If publishing fails

SituationWhat to do
The site is not registeredThe error lists the registered site IDs. Check --site and the delivery target in the config, or ask the admin to register the site.
“registered to … selected checkout is …”The repository or directory differs from the registration. Run in a checkout of the registered repository and pass the registered directory.
Symbolic links in the sourceReplace them with real files, or move them out of the directory.
The site's lock is heldAnother publish or a registry sync that changes this site is running; retry later. If a crashed run left the lock behind, the admin checks it with lock inspect --site and releases it with lock recover.
Failed after some changesFix the cause and run the same command again. It completes the remaining changes.
