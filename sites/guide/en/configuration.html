For admins

Configuration

Every artifact-pages command reads one YAML deployment config, usually artifact-pages.yaml in the admin repository. It names the delivery target and, for the registry commands, the complete set of sites. Satellite repositories, the ones that only publish their own documents, have no config file; they point at the admin repository's.

The file at a glance

One file holds two kinds of settings: where to deliver (the provider and its settings) and which sites exist (sites). It holds no secrets; credentials come from the environment.

artifact-pages.yaml / ADMIN REPOSITORY
schemaVersion: 1             # always the integer 1
provider: local              # local, aws, or cloudflare
local:                       # the block for that provider, and only that one
  root: .local/storage
sites:                       # the complete set of registered sites
  checkout:
    name: Payments / Checkout
    description: Checkout design, incidents, and runbooks.
    repository: acme/checkout
    sourcePath: docs/artifacts
KeyMeaning
schemaVersionRequiredThe integer 1.
providerRequiredThe delivery target: local, aws, or cloudflare. A shared base layer may omit it (see layers).
local / aws / cloudflareRequiredExactly the settings block that matches provider. See delivery targets.
cli / webOptionalEach holds an exact version (MAJOR.MINOR.PATCH): the CLI that runs and the reader app that app deploy installs. Set each in at most one layer. See Pinning and upgrading versions.
sitesOptionalThe sites to register, keyed by site ID. Required by registry register and registry unregister. See sites.

The file is checked strictly: unknown or duplicate keys, more than one YAML document, and values of the wrong type are errors rather than being ignored. The example site is illustrative.

Which file is used

Each command looks for its config in this order and uses the first one it finds. A config doesn't have to be named artifact-pages.yaml when it is chosen explicitly.

  1. --config LOCATOR

    A local path or a github:// locator. Repeat it to stack local files as layers.

  2. ARTIFACT_PAGES_CONFIG

    An environment variable holding one locator.

  3. artifact-pages.yaml in the current directory

    The default, so commands run in the admin repository need no option. A satellite repository has no such file; it uses the first or second item.

  4. Your saved default

    One locator saved in your user config directory with artifact-pages config set-default LOCATOR. Nothing else is saved there, and never credentials.

Commands that use a delivery target print it (for example the bucket) in their output, so you can see which target a run used.

Layers

To reuse one list of sites with different delivery targets, keep sites in a shared file and the target in a second file, then pass both with --config in order.

artifact-pages.yaml / SHARED
schemaVersion: 1
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
.local/artifact-pages.local.yaml / NOT COMMITTED
schemaVersion: 1
provider: local
local:
  root: .local/storage
TERMINAL / ADMIN
$ artifact-pages registry register --config artifact-pages.yaml --config .local/artifact-pages.local.yaml --dry-run
  • Every layer has schemaVersion: 1. A layer that sets provider also has exactly the matching block.
  • A later target replaces the earlier one as a whole; provider settings are never merged.
  • A later layer without sites keeps the earlier list. A later layer with sites replaces the whole list, even when it is {}; sites are never merged one by one.
  • cli and web may be set by only one layer, even when two layers give the same value; a second layer that sets either is an error. One layer may set both.
  • Only repeated --config options make layers. Overlay files are never picked up automatically.

Remote config

A satellite repository has no config file of its own. It points --config (or ARTIFACT_PAGES_CONFIG, or the Action's config input) at the admin repository's file with a github:// locator. This is the normal form for any repository other than the admin one:

TERMINAL / acme/checkout
$ artifact-pages site publish --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --dry-run

To pin the config to one commit, add ?ref= and quote the locator because of the ?:

TERMINAL / acme/checkout
$ artifact-pages site publish --site checkout --source docs/artifacts --config 'github://acme/platform-admin/artifact-pages.yaml?ref=0123456789abcdef0123456789abcdef01234567' --dry-run
  • The form is github://OWNER/REPO/FILE?ref=REF. Without FILE, artifact-pages.yaml is read. Without ref, the default branch is resolved to one commit for the whole command, so a run cannot change target midway. Add ref with a full commit SHA only when you want the config itself to change by review in your repository.
  • Quote the locator in the shell when it has a ?ref=. Private repositories are read with GITHUB_TOKEN or GH_TOKEN; in the Actions, with the github-token input (see A private admin repository).
  • The file is fetched again on every run, and the output shows the config commit it used.
  • A remote config must be complete; it cannot be combined with other layers.
  • A single repository that is both admin and site may keep a local artifact-pages.yaml instead; that is the exception.
  • It only tells the command where to deliver. Whether a repository may publish to a site is still decided by the registry on the delivery target.

acme/platform-admin is an illustrative admin repository.

A private admin repository

A site repository's workflow token (GITHUB_TOKEN) can read only that repository, so it cannot read a private admin repository. The Action's github-token input takes a token that can. A GitHub App installation token fits well: it belongs to the App rather than to a person, reaches only the repositories you install the App on, and each job mints its own short-lived token.

  1. Create a GitHub App

    Under Settings → Developer settings → GitHub Apps of the account or organization that owns the repositories. Turn Webhook → Active off; the App only issues tokens. Set the repository permissions to Contents: Read-only and Metadata: Read-only. Add Pull requests only for repositories that run previews: Read-only is enough for the pull-request check, and Read and write if previews post comments (comment: true). Then generate a private key (a .pem file).

  2. Install it on only the repositories that need it

    Choose Only select repositories: the admin repository and the site repositories that publish. Do not install it on all repositories.

  3. Store the App ID and key in each site repository

    Under Settings → Secrets and variables → Actions, add the App ID as a variable (ARTIFACT_PAGES_APP_ID below) and the private key as a secret (ARTIFACT_PAGES_APP_PRIVATE_KEY). The names are illustrative. The key is the only secret in this pattern; no token value is ever stored.

  4. Mint a token in the job and pass it as github-token

    Add actions/create-github-app-token before the Action. Limit the token with repositories and permission-* to what this job needs.

    .github/workflows/publish-docs.yml / acme/checkout (excerpt)
    permissions:
  contents: read

jobs:
  publish:
    runs-on: ubuntu-24.04
    steps:
      - name: Mint a GitHub App token
        id: app-token
        uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
        with:
          app-id: ${{ vars.ARTIFACT_PAGES_APP_ID }}
          private-key: ${{ secrets.ARTIFACT_PAGES_APP_PRIVATE_KEY }}
          owner: ${{ github.repository_owner }}
          repositories: platform-admin        # the admin repository only
          permission-contents: read
      - uses: artifact-pages/publish-action@vX.Y.Z
        with:
          site: checkout
          source: docs/artifacts
          config: github://acme/platform-admin/artifact-pages.yaml
          github-token: ${{ steps.app-token.outputs.token }}
        env:
          CF_API_TOKEN: ${{ secrets.CF_API_TOKEN }}
          # provider credentials from secrets, as in the publishing example
  • Two tokens, two jobs. github-token reads the config. The history fetch that deepens a shallow checkout always uses the workflow token, which can read the site repository; github-token is never used for it. So permissions: contents: read stays enough for the workflow, and the App token for a publish job needs the admin repository only.
  • Preview jobs need more. A preview job also uses github-token to check the pull request in the site repository and to post the comment. Mint it with repositories: platform-admin,checkout, permission-contents: read and permission-pull-requests: write (read if the job does not comment). The comment is then written by the App's bot account.
  • Why not a personal access token? It is tied to one person's account and usually reaches more than the admin repository. A fine-grained token limited to Contents: Read-only on the admin repository should also work, but this route has not been verified.
  • On GitHub Free, private repositories cannot use environment secrets or deployment branch policies. Store the secrets at repository scope and drop environment: from the workflow. Any workflow run in the repository can then read them, not only runs on main, so keep real publishing behind the Action's publish-on input and keep previews gated to same-repository pull requests. Review changes to workflow files like changes to credentials.

If the config cannot be read, the error starts with cannot read deployment config followed by the locator, and the command exits with code 2. The token is never printed.

Delivery targets

The provider block says where the reader app and the published sites are stored. Sites, URLs, and commands are the same for every provider.

local: a directory

Writes to a directory on this machine, for development and for trying things out. Serve it with a local web server.

KeyMeaning
rootRequiredThe output directory, such as .local/storage. It must not overlap a site's source directory.

aws: S3 and CloudFront

artifact-pages.yaml / AWS
provider: aws
aws:
  region: ap-northeast-1
  accountId: "123456789012"     # bucket becomes artifact-pages-123456789012-ap-northeast-1
  distributionId: E1234567890ABC
KeyMeaning
regionRequiredThe bucket's AWS region.
bucketOptionalThe S3 bucket. When set, it always wins.
accountIdOptionalA quoted 12-digit string. Required only when bucket is omitted; the bucket is then artifact-pages-<accountId>-<region>. It is never looked up from your credentials.
distributionIdOptionalThe CloudFront distribution to send cache refresh requests to. Without it, no refresh is requested.

cloudflare: R2 and the Cloudflare cache

artifact-pages.yaml / CLOUDFLARE
provider: cloudflare
cloudflare:
  accountId: "<32-character account ID>"
  zoneId: "<32-character zone ID>"
  publicBaseURL: https://docs.example.com
  # bucket defaults to artifact-pages; credential variable names use their defaults
KeyMeaning
accountIdRequiredThe Cloudflare account that owns the R2 bucket (32 hexadecimal characters).
zoneIdRequiredThe zone whose cache is purged after changes (32 hexadecimal characters).
publicBaseURLRequiredThe public HTTPS origin readers use, without a path. Purge requests are built from it.
bucketOptionalThe R2 bucket. Defaults to artifact-pages.
accessKeyIdEnv, secretAccessKeyEnvOptionalNames of the environment variables holding the R2 access key. Default CF_R2_ACCESS_KEY_ID and CF_R2_SECRET_ACCESS_KEY.
apiTokenEnvOptionalName of the variable holding the API token used for cache purges. Default CF_API_TOKEN.
sessionTokenEnvOptionalName of a variable holding a session token, when the R2 credential is temporary.
registryReaderAccessKeyIdEnv, registryReaderSecretAccessKeyEnv, registryReaderSessionTokenEnvOptionalA separate read-only credential that site publish and preview publish use only to read the site registry. Set the first two together. See credentials.

The values shown are placeholders. Setting up the bucket, hostname, cache rules, and preview retention is done in Cloudflare or AWS itself (for example with Terraform), not in this file. The command also accepts a gcp-local provider, which is an emulator profile for tests, not a production target.

Credentials

The config only names environment variables; it never contains credential values. Give each job only what it needs.

  • AWS uses the standard AWS credential chain: environment variables, profiles, or a role assumed in CI (for example through GitHub Actions OIDC).
  • Cloudflare reads the variables named in the cloudflare block. Which ones a command needs:
CommandR2 access key and secretRegistry readerAPI token
site publishRequiredUsed only if configuredFor any run that changes the site or retries an unfinished purge; checked before anything is written
preview publishRequiredUsed only if configuredNot needed
registry register, registry unregisterRequiredNot usedFor any run that changes the registry or removes a site; checked before anything is written
app deployRequiredNot usedFor any run that changes the app; checked before anything is written
lock inspect, lock recoverRequiredNot usedNot needed
index build, config set-defaultNot neededNot usedNot needed

The token is what lets the CLI ask Cloudflare to purge the changed URLs, so a run that changes content stops before writing if it is missing. Dry runs and runs with nothing to change never need it. A team's publishing job should be able to read the site registry; read, write, and delete only its own site's files and cache-retry record (_control/site-cache/<site>.json); read and write its previews and lock; and request a cache refresh from the CDN (a CloudFront invalidation on AWS, a zone cache purge on Cloudflare). It never needs to write the registry or the reader app. With the registry-reader fields set, the registry is read with that separate credential, so the main credential can be limited to the site. If those fields are set but their values are missing, the publish stops instead of falling back.

Sites

sites maps each site ID to where its content comes from.

FieldRules
Site ID (the key)RequiredLowercase letters and digits, separated by single hyphens, such as checkout or mobile-ios. It appears in URLs. assets is reserved.
nameRequiredThe display name. Spaces and punctuation are fine; two sites may share a name.
descriptionOptionalA short line shown with the site in the site list and the @ palette.
repositoryRequiredExactly owner/repo on GitHub; not a URL and not ending in .git. Compared without regard to case.
sourcePathRequiredThe directory to publish, relative to the repository root, with / separators; . means the root. No leading /, .., or backslashes. Compared exactly.

A repository and directory pair can belong to only one site, but one repository can publish several sites from different directories. There is no branch setting: the team's workflow decides which branch publishes.

COMPLETE SET

sites lists every site that should exist. A site missing from it is unregistered by the next registry register, and its published pages, index, and previews are deleted. Always review the dry run.

Leaving sites out is an error for the registry commands, never an empty list. To have no sites, write sites: {}.

Only the registry commands read sites. site publish and preview publish check the registry deployed on the delivery target, so a team's config may contain only the target.

Apply changes to sites

After editing sites, apply it from the admin repository. Plan with --dry-run first.

TERMINAL / ADMIN
# Add, change, or remove sites to match the file
$ artifact-pages registry register --dry-run
$ artifact-pages registry register
# Or remove one site: delete it from sites first, then
$ artifact-pages registry unregister --site billing --dry-run
$ artifact-pages registry unregister --site billing
  • registry register makes the deployed registry match the file and cleans up sites that were removed from it.
  • registry unregister --site ID requires that the site is already gone from the file. It removes the registration, deletes that site's content and previews, and asks the CDN to refresh. It is safe to run again if it stops partway.
  • Deleted content can stay in caches for a short time, and pages a reader already opened cannot be recalled.
  • If a crashed run leaves a lock, check it with lock inspect --scope registry (or --site ID) and, once you are sure nothing is running, release it with lock recover … --observed-etag ETAG using the value you saw.

The same file also tells app deploy where to install the reader app. It installs the reader app release that web.version names; releases are listed on GitHub Releases, and Pinning and upgrading versions covers upgrades. To install the CLI and try the whole flow with provider: local, see Getting started.
