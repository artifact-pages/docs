管理者向け

設定ファイル

artifact-pagesのコマンドは、どれも1つのYAMLの設定ファイルを読みます。ふつうは管理リポジトリにあるartifact-pages.yamlです。配信先と、registry syncで使うサイトの定義をここに書きます。自分の文書を公開するだけのサテライトリポジトリには設定ファイルを置かず、管理リポジトリのファイルを指定します。

ファイルの全体像

1つのファイルに、どこへ配信するか（プロバイダーとその設定）と、どのサイトがあるか（sites）の2種類を書きます。秘密の値は書きません。認証情報は環境変数から渡します。

artifact-pages.yaml / 管理リポジトリ
schemaVersion: 1             # 常に整数の 1
provider: local              # local、aws、cloudflare のいずれか
local:                       # そのプロバイダーの設定だけを書く
  root: .local/storage
sites:                       # 登録するサイトの全部
  checkout:
    name: 決済チーム / Checkout
    description: 決済画面とAPIの設計、障害対応、運用手順。
    repository: acme/checkout
    sourcePath: docs/artifacts
キー意味
schemaVersion必須整数の1。
provider必須配信先の種類。local、aws、cloudflareのいずれか。共通部分だけを書いた土台のファイルでは省略できます（重ね合わせ）。
local / aws / cloudflare必須providerに対応する設定のブロックを1つだけ書きます。配信先を参照してください。
cli / web任意それぞれ正確なversion（MAJOR.MINOR.PATCH）を持ち、動くCLIと、app deployが置く閲覧アプリを決めます。それぞれ、書けるのは多くても1つのファイルです。「バージョンの固定と更新」を参照してください。
sites任意登録するサイト。サイトIDをキーにします。registry syncでは必須で、その全体が配信先に置くべき登録の内容になります。sitesを参照してください。

ファイルは厳密に検査されます。知らないキー、重複したキー、複数のYAMLドキュメント、型の違う値は、無視されずにエラーになります。例のサイトは説明用です。

使われるファイルの決まり方

コマンドは次の順に設定を探し、最初に見つかったものを使います。明示して指定するなら、ファイル名はartifact-pages.yamlでなくてもかまいません。

  1. --config LOCATOR

    ローカルのパスか、github://の指定。繰り返し指定すると、ローカルのファイルを重ね合わせます。

  2. ARTIFACT_PAGES_CONFIG

    指定を1つ入れた環境変数。

  3. いまのディレクトリのartifact-pages.yaml

    既定のファイル。管理リポジトリで実行するなら、オプションはいりません。サテライトリポジトリにこのファイルはなく、1番目か2番目を使います。

  4. 保存した既定の指定

    artifact-pages config set-default LOCATORで、ユーザーの設定ディレクトリに指定を1つ保存できます。保存されるのはこの指定だけで、認証情報は保存されません。

配信先を使うコマンドは、使った配信先（バケットなど）を出力に表示します。どの配信先に対して実行したかを確かめられます。

重ね合わせ

同じサイトの定義を、別の配信先でも使いたいことがあります。そのときはsitesを共通のファイルに、配信先を別のファイルに書き、--configで順に渡します。

artifact-pages.yaml / 共通
schemaVersion: 1
sites:
  checkout:
    name: 決済チーム / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts
.local/artifact-pages.local.yaml / コミットしない
schemaVersion: 1
provider: local
local:
  root: .local/storage
ターミナル / 管理者
$ artifact-pages registry sync --config artifact-pages.yaml --config .local/artifact-pages.local.yaml --dry-run
  • どのファイルにもschemaVersion: 1を書きます。providerを書いたファイルには、対応するブロックも1つだけ書きます。
  • あとのファイルの配信先は、前の配信先をまるごと置き換えます。プロバイダーの設定が混ざることはありません。
  • あとのファイルにsitesがなければ、前の一覧を引き継ぎます。sitesがあれば、{}であっても一覧全体を置き換えます。サイト単位で混ざることはありません。
  • cliとwebを書けるのは1つのファイルだけです。2つのファイルが同じ値でも、2つめのファイルが書くとエラーになります。1つのファイルに両方を書くのは問題ありません。
  • 重ね合わせになるのは、--configを繰り返したときだけです。上書き用のファイルを自動で探すことはありません。

リモートの設定ファイル

サテライトリポジトリは、自分の設定ファイルを持ちません。--config（またはARTIFACT_PAGES_CONFIG、Actionのconfig入力）に、管理リポジトリのファイルを指すgithub://の指定を渡します。管理リポジトリ以外では、これが通常の形です。

ターミナル / acme/checkout
$ artifact-pages site sync --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --dry-run

設定を1つのコミットに固定するときは?ref=を付けます。?を含むので、指定をクォートで囲みます。

ターミナル / acme/checkout
$ artifact-pages site sync --site checkout --source docs/artifacts --config 'github://acme/platform-admin/artifact-pages.yaml?ref=0123456789abcdef0123456789abcdef01234567' --dry-run
  • 形式はgithub://OWNER/REPO/FILE?ref=REFです。FILEを省くとartifact-pages.yamlを読みます。refを省くと、デフォルトブランチをその時点のコミットに決め、コマンドの最後までそのコミットを使います。そのため、実行の途中で配信先が変わることはありません。設定そのものをリポジトリ側のレビューで変えたいときだけ、refに完全なコミットSHAを指定します。
  • ?ref=を付けるときは、シェルではクォートで囲みます。非公開リポジトリはGITHUB_TOKENかGH_TOKENで読みます。Actionsではgithub-token入力で渡します（非公開の管理リポジトリを読むを参照）。
  • ファイルは実行のたびに取り直し、使ったコミットを出力に表示します。
  • リモートの設定ファイルは、それだけで完結している必要があります。ほかのファイルとは重ねられません。
  • 管理と公開を1つのリポジトリで兼ねる場合に限り、ローカルのartifact-pages.yamlを置いてもかまいません。これは例外です。
  • この指定で決まるのは配信先だけです。そのリポジトリがサイトに公開してよいかどうかは、配信先にある登録情報で判断します。

acme/platform-adminは説明用の管理リポジトリです。

非公開の管理リポジトリを読む

サイトのリポジトリのワークフローが持つトークン（GITHUB_TOKEN）で読めるのは、そのリポジトリだけです。そのため、非公開の管理リポジトリは読めません。Actionのgithub-token入力には、読めるトークンを渡します。GitHub Appのインストールトークンが向いています。トークンの持ち主は人ではなくAppで、届く範囲はAppをインストールしたリポジトリに限られます。また、ジョブごとに有効期間の短いトークンを発行できます。

  1. GitHub Appを作る

    リポジトリを持つアカウントまたはOrganizationのSettings → Developer settings → GitHub Appsから作ります。Appはトークンを発行するだけなので、Webhook → Activeはオフにします。リポジトリの権限はContents: Read-onlyとMetadata: Read-onlyです。Pull requestsは、プレビューを実行するリポジトリ向けにだけ加えます。プルリクエストの確認にはRead-onlyで足り、プレビューでコメントを投稿する（comment: true）ならRead and writeが必要です。最後に、秘密鍵（.pemファイル）を生成します。

  2. 必要なリポジトリにだけインストールする

    Only select repositoriesを選び、管理リポジトリと、公開を行うサイトのリポジトリだけを指定します。すべてのリポジトリには入れません。

  3. AppのIDと鍵をサイトのリポジトリに登録する

    Settings → Secrets and variables → Actionsで、App IDを変数（下の例ではARTIFACT_PAGES_APP_ID）に、秘密鍵をシークレット（ARTIFACT_PAGES_APP_PRIVATE_KEY）に登録します。名前は説明用です。この方法でシークレットとして持つのは鍵だけで、トークンの値を保存することはありません。

  4. ジョブの中でトークンを発行し、github-tokenに渡す

    Actionの前にactions/create-github-app-tokenを置きます。repositoriesとpermission-*で、そのジョブに必要な範囲だけに絞ります。

    .github/workflows/publish-docs.yml / acme/checkout（抜粋）
    permissions:
  contents: read

jobs:
  publish:
    runs-on: ubuntu-24.04
    steps:
      - name: Mint a GitHub App token
        id: app-token
        uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
        with:
          app-id: ${{ vars.ARTIFACT_PAGES_APP_ID }}
          private-key: ${{ secrets.ARTIFACT_PAGES_APP_PRIVATE_KEY }}
          owner: ${{ github.repository_owner }}
          repositories: platform-admin        # 管理リポジトリだけ
          permission-contents: read
      - uses: artifact-pages/publish-action@vX.Y.Z
        with:
          site: checkout
          source: docs/artifacts
          config: github://acme/platform-admin/artifact-pages.yaml
          github-token: ${{ steps.app-token.outputs.token }}
        env:
          CF_API_TOKEN: ${{ secrets.CF_API_TOKEN }}
          # プロバイダーの認証情報は、公開の例と同じくシークレットから渡す
  • トークンは用途ごとに2つあります。github-tokenは設定ファイルを読むためのものです。浅いチェックアウトを深くする履歴の取得には、常にワークフローのトークンを使います。このトークンならサイトのリポジトリを読めます。github-tokenが履歴の取得に使われることはありません。したがって、ワークフローの権限はcontents: readのままで足り、公開ジョブのAppトークンに必要なのは管理リポジトリだけです。
  • プレビューのジョブには、もう少し権限が要ります。プレビューのジョブは、サイトのリポジトリのプルリクエストを確認し、コメントを投稿するときにもgithub-tokenを使います。トークンはrepositories: platform-admin,checkout、permission-contents: read、permission-pull-requests: writeで発行します（コメントしないジョブならreadで足ります）。コメントは、Appのボットアカウントの名前で投稿されます。
  • 個人用アクセストークンを使わない理由。個人用アクセストークンは特定の人のアカウントに結びつき、管理リポジトリ以外にも届くことが多いからです。管理リポジトリのContents: Read-onlyだけに絞ったファイングレインドトークンでも読めるはずですが、この方法は検証していません。
  • GitHub Freeでは、非公開リポジトリでEnvironmentのシークレットやデプロイ先のブランチ制限を使えません。シークレットはリポジトリのスコープに置き、ワークフローからenvironment:を外します。その場合、main以外で動くワークフローも含め、リポジトリ内のどのワークフローの実行からもシークレットを読めます。実際の公開はActionのpublish-on入力で絞り、プレビューは同じリポジトリのプルリクエストに限ってください。ワークフローファイルの変更は、認証情報の変更と同じ扱いでレビューします。

設定ファイルを読めないときのエラーは、cannot read deployment configに続けて指定した場所を示し、終了コードは2です。トークンは表示されません。

メッセージ考えられる原因対処
GitHub returned HTTP 404; … may be private and no token was providedローカルで実行していて、GITHUB_TOKENもGH_TOKENも設定していません。管理リポジトリのcontents:readを持つトークンを、どちらかに設定します。
GitHub returned HTTP 404, which it uses both for missing repositories and for private repositories the token cannot accessトークンで見えない非公開リポジトリに対して、GitHubは403ではなく404を返します。Actionsでgithub-tokenを渡さない場合も、ワークフローのトークンが送られるため、このメッセージになります。ほかに、指定の誤り、管理リポジトリにAppを入れていない、repositoriesに管理リポジトリがない、Contentsの権限がない、などが考えられます。指定を確認します。管理リポジトリにAppがインストールされていること、発行したトークンのrepositoriesに管理リポジトリが入っていること、permission-contents: readを付けていることを確かめます。トークンはgithub-tokenに渡します。
the config path or ref does not exist in … (HTTP 404)リポジトリには届いていますが、ファイルか?ref=が間違っています。指定のファイル名と、ブランチ、タグ、コミットSHAを確認します。
GitHub rejected the token (HTTP 401)トークンが無効か、期限切れです。Appのトークンの有効期間は1時間です。トークンは、それを使うジョブの中で発行し、そのまま渡します。
GitHub denied access (HTTP 403); the token lacks permissionトークンが管理リポジトリのcontents:readを持っていません。AppにContents: Read-onlyを付与します。新しい権限の承認をGitHubに求められたら、インストール側で承認します。
GitHub denied access (HTTP 403) because the API rate limit is exhaustedトークンのAPIレート制限を使い切っています。制限がリセットされるまで待つか、上限の高いトークンを使います。

たとえば、非公開の管理リポジトリを読めるトークンがない状態で、GitHub Actionsのホステッドランナー上の公開を実行すると、次のメッセージが出ました（リポジトリ名は説明用のものに置き換えています）。

ERROR / HOSTED RUNNER
error: cannot read deployment config github://acme/platform-admin/artifact-pages.yaml: GitHub returned HTTP 404, which it uses both for missing repositories and for private repositories the token cannot access. Check the locator, and that the token (for example a GitHub App installation or fine-grained PAT) has contents:read on acme/platform-admin.

acme/platform-adminとacme/checkoutは説明用のリポジトリです。ARTIFACT_PAGES_APP_IDとARTIFACT_PAGES_APP_PRIVATE_KEYも説明用の名前です。

配信先

プロバイダーのブロックには、閲覧アプリと公開したサイトを置く場所を書きます。サイト、URL、コマンドは、どのプロバイダーでも同じです。

local：ローカルのディレクトリ

手元のディレクトリに書き出します。開発や、試しに動かすときに使い、ローカルのWebサーバーで配信します。

キー意味
root必須書き出し先のディレクトリ。たとえば.local/storage。サイトの公開元のディレクトリと重なってはいけません。

aws：S3とCloudFront

artifact-pages.yaml / AWS
provider: aws
aws:
  region: ap-northeast-1
  accountId: "123456789012"     # バケットは artifact-pages-123456789012-ap-northeast-1
  distributionId: E1234567890ABC
キー意味
region必須バケットのあるAWSリージョン。
bucket任意S3のバケット。書いた場合は常にこちらを使います。
accountId任意12桁の数字を文字列で（クォートして）書きます。bucketを省くときだけ必要で、バケットはartifact-pages-<accountId>-<region>になります。認証情報から調べることはしません。
distributionId任意キャッシュの更新を依頼するCloudFrontのディストリビューション。書かなければ更新は依頼しません。

cloudflare：R2とCloudflareのキャッシュ

artifact-pages.yaml / CLOUDFLARE
provider: cloudflare
cloudflare:
  accountId: "<32文字のアカウントID>"
  zoneId: "<32文字のゾーンID>"
  publicBaseURL: https://docs.example.com
  # bucket は既定で artifact-pages、認証情報の変数名も既定のまま
キー意味
accountId必須R2のバケットを持つCloudflareのアカウント（16進数32文字）。
zoneId必須変更後にキャッシュを消すゾーン（16進数32文字）。
publicBaseURL必須読者が使う公開アドレス（HTTPS、パスなし）。キャッシュを消す依頼はこのアドレスで組み立てます。
bucket任意R2のバケット。既定はartifact-pages。
accessKeyIdEnv、secretAccessKeyEnv任意R2のアクセスキーを入れる環境変数の名前。既定はCF_R2_ACCESS_KEY_IDとCF_R2_SECRET_ACCESS_KEY。
apiTokenEnv任意キャッシュを消すときに使うAPIトークンの変数名。既定はCF_API_TOKEN。
sessionTokenEnv任意R2の認証情報が一時的なものの場合に、セッショントークンを入れる変数名。
registryReaderAccessKeyIdEnv、registryReaderSecretAccessKeyEnv、registryReaderSessionTokenEnv任意site syncとpreview publishが、サイトの登録情報を読むときだけに使う、読み取り専用の別の認証情報。最初の2つは組で設定します。認証情報を参照してください。

値はすべて仮のものです。バケット、ホスト名、キャッシュのルール、プレビューの保持期間は、このファイルではなくCloudflareやAWS側（Terraformなど）で設定します。なお、コマンドはgcp-localというプロバイダーも受け付けますが、これはテスト用のエミュレーター向けで、本番の配信先ではありません。

認証情報

設定ファイルには環境変数の名前だけを書き、認証情報の値は書きません。それぞれのジョブには、必要なものだけを渡します。

  • AWSは、AWSの標準の認証情報の探し方に従います。環境変数、プロファイル、CIで引き受けるロール（GitHub ActionsのOIDCなど）が使えます。
  • Cloudflareは、cloudflareブロックで名前を指定した環境変数を読みます。コマンドごとに必要なものは次のとおりです。
コマンドR2のアクセスキーとシークレット登録情報の読み取り用APIトークン
site sync必須設定したときだけ使うサイトを変える実行と、終わっていないキャッシュ削除をやり直す実行で必要。書き込む前に確認する
preview publish必須設定したときだけ使う不要
registry sync必須使わない登録情報を変える実行、サイトを削除する実行ではすべて必要。書き込む前に確認する
app deploy必須使わないアプリを変える実行ではすべて必要。書き込む前に確認する
lock inspect、lock recover必須使わない不要
index build、config set-default不要使わない不要

APIトークンは、変わったURLのキャッシュ削除をCloudflareに依頼するために使います。内容を変える実行でトークンがないと、何も書き込まずに止まります。ドライランと、変更がない実行では、APIトークンはいりません。チームの公開ジョブに許可するのは、サイトの登録情報の読み取りと、そのサイトのファイルとキャッシュ再試行の記録（_control/site-cache/<site>.json）の読み取り・書き込み・削除、プレビューとロックの読み取り・書き込み、それにCDNへのキャッシュ更新の依頼（AWSではCloudFrontの無効化、Cloudflareではゾーンのキャッシュ削除）だけです。登録情報や閲覧アプリへの書き込みは必要ありません。登録情報の読み取り用の項目を設定すると、登録情報はその別の認証情報で読むので、主な認証情報をそのサイトだけに絞れます。項目を設定したのに値がない場合は、主な認証情報で代用せずに、公開を止めます。

sites

sitesには、サイトIDごとに、中身をどこから公開するかを書きます。

項目決まり
サイトID（キー）必須英小文字と数字を、1つのハイフンでつなげたもの。checkoutやmobile-iosなど。URLに使われます。assetsは予約されていて使えません。
name必須表示名。空白や記号を含めてもよく、ほかのサイトと同じ名前でもかまいません。
description任意サイトの一覧と@のパレットで、サイト名に添えて表示する短い説明。
repository必須GitHubのowner/repoそのもの。URLや、末尾が.gitの値は使えません。大文字と小文字は区別せずに比べます。
sourcePath必須公開するディレクトリ。リポジトリのルートからの相対パスを/区切りで書き、ルートは.です。先頭の/、..、バックスラッシュは使えません。文字列のまま比べます。

同じリポジトリと同じディレクトリの組は、1つのサイトにしか登録できません。1つのリポジトリの別々のディレクトリから、複数のサイトを公開することはできます。ブランチの設定はなく、どのブランチから公開するかはチームのワークフローで決めます。

全件を書く

sitesには、あるべきサイトをすべて書きます。一覧から消えたサイトは次のregistry syncで登録が取り下げられ、公開したページ、インデックス、プレビューが削除されます。必ずドライランの結果を確かめてください。

registry syncでsitesそのものを書かないとエラーになり、空の一覧としては扱われません。サイトを1つも置かないときはsites: {}と書きます。

sitesを読むのはregistry syncだけです。site syncとpreview publishは配信先にある登録情報を確認するので、チーム側の設定ファイルには配信先だけを書いておけば足ります。

サイトの変更を反映する

sitesを編集したら、管理リポジトリから反映します。まず--dry-runで計画を確かめます。

ターミナル / 管理者
# ファイルに合わせてサイトを追加・変更・削除する
$ artifact-pages registry sync --dry-run
$ artifact-pages registry sync
  • registry syncは、配信先の登録情報をファイルに合わせます。sitesの全体が、あるべき登録の内容として扱われるため、sitesは必須です。
  • サイトを外すには、sitesから消してregistry syncを実行します。サイトの登録を解除する別のコマンドはありません。コマンドはそのサイトを取り下げ、中身とプレビューを削除して、CDNにキャッシュの更新を依頼します。片付ける内容は記録されるので、途中で止まっても、設定ファイルからそのサイトが消えたあとに実行したregistry syncが続きを終わらせます。
  • 変更がなければ結果はno-op、変更を反映できたときはsyncedです。
  • 削除した中身がしばらくキャッシュに残ることがあり、読者がすでに開いたページは取り消せません。
  • 止まった実行がロックを残したときは、lock inspect --scope registry（サイトのロックなら--site ID）で確認します。何も実行されていないことを確かめてから、確認したときの値をlock recover … --observed-etag ETAGに渡して解除します。

同じファイルは、閲覧アプリを置くapp deployでも配信先として使います。app deployが置くのは、web.versionで指定したリリースの閲覧アプリです。リリースはGitHub Releasesで確認でき、更新の手順は「バージョンの固定と更新」にあります。CLIの入れ方と、provider: localで一連の流れを試す手順は「はじめる」にあります。
