はじめて導入する管理者向け

はじめる

artifact-pagesコマンドを入れ、管理リポジトリとチームのリポジトリがそれぞれ何をするかを確認してから、配信先にCloudflareを使う例で、最初のサイトを公開して閲覧アプリで読むところまで進めます。

CLIを入れる

閲覧アプリの配置、サイトの登録、公開は、どれもartifact-pagesというひとつのコマンドで行います。GitHub Releasesの各CLIリリースには、LinuxとmacOS（amd64とarm64）向けの単体のバイナリと、チェックサムのファイルが付いています。Windowsは対象外です。

ターミナル / インストール
$ VERSION=x.y.z
$ OS=$(uname -s | tr A-Z a-z)
$ ARCH=$(uname -m | sed -e 's/x86_64/amd64/' -e 's/aarch64/arm64/')
$ BASE=https://github.com/artifact-pages/artifact-pages/releases/download/v$VERSION
$ curl -fsSLO "$BASE/artifact-pages_v${VERSION}_${OS}_${ARCH}"
$ curl -fsSLO "$BASE/artifact-pages_v${VERSION}_checksums.txt"
$ grep "artifact-pages_v${VERSION}_${OS}_${ARCH}\$" "artifact-pages_v${VERSION}_checksums.txt" | shasum -a 256 -c -
$ install -m 0755 "artifact-pages_v${VERSION}_${OS}_${ARCH}" ~/.local/bin/artifact-pages
$ artifact-pages version
  • x.y.zはリリースのバージョンです。タグやファイル名に付く先頭のvは付けずに書きます。バイナリは、リリースのアセットartifact-pages_vX.Y.Z_<os>_<arch>で、<os>はlinuxかdarwin、<arch>はamd64かarm64です。アーカイブではないので、展開は要りません。
  • チェックサムの確認はOKと表示される必要があります。チェックサムのファイルはバイナリと同じリリースのものなので、壊れたダウンロードや途中までのアップロードは見つけられますが、リリース自体が改ざんされた場合は見つけられません。確認に通らないバイナリは実行しないでください。
  • バイナリをPATHの通った場所に置きます。どのディレクトリでも構いません。~/.local/binは一例で、先に作っておきます。
  • 入れたCLIは出発点です。設定ファイルにcli.versionがあれば、入れたコマンドがそのリリースをダウンロードしてチェックサムを確かめ、そちらを実行します（下のコールアウトを参照）。リリースには、組み込んだGoモジュールのライセンスと、互換性のファイルartifact-pages_vX.Y.Z_compatibility.jsonも付いています。
バージョン

閲覧アプリと、動くCLIは、設定ファイルで決めます。artifact-pages.yamlのweb.versionが、app deployの置く閲覧アプリのリリースを決め、任意のcli.versionがCLIを決めます。この2つは別々にリリースされます。固定のしかたと更新の手順は「バージョンの固定と更新」にあります。

2種類のリポジトリ

ひとつの環境には、管理リポジトリがひとつと、チームのリポジトリ（サテライトリポジトリ）がいくつでもあります。サイトを増やしたいチームは、管理リポジトリにプルリクエストを出します。管理者がそれを承認してマージし、環境に反映します。各チームは、登録された自分のサイトだけを公開します。

管理リポジトリは、配信先と、登録するサイトの一覧をすべて持ちます。管理者は、承認した変更から閲覧アプリを置き、サイトを登録します。チームのリポジトリに置くのは、文書とワークフロー1つだけです。設定ファイルは置かず、管理リポジトリのartifact-pages.yamlをgithub://の指定で読みます。あるリポジトリがそのサイトに公開してよいかは、チームの設定ファイルではなく、配信先にあるサイトの登録情報で決まります。

Cloudflareで始める

配信先にCloudflareを使う例で、最初のサイトを読めるところまで進めます。管理リポジトリのacme/platform-adminと、チームのリポジトリのacme/checkoutは説明用の例です。AWSでも流れとコマンドは同じで、変わるのは手順1と2です（ほかの配信先）。

  1. 配信先を用意する

    非公開のR2のバケットをひとつ作り、読者が使うホスト名（例ではdocs.example.com）につなぎます。あわせて、閲覧アプリへの経路の振り分け、/_control/の遮断、キャッシュのルール、プレビューの保持期間を設定します。これらはArtifact Pagesのコマンドでは作らず、Terraformなどで用意します。製品リポジトリに、そのためのTerraformのモジュールがあります。管理者の認証情報として、R2のアクセスキーとシークレット、キャッシュを消す権限を持つAPIトークンも用意します。

    詳しい手順は、製品リポジトリのCloudflare deployment（英語）を参照してください。

  2. 管理リポジトリにartifact-pages.yamlを書く

    配信先にcloudflareを指定し、置く閲覧アプリのリリースをweb.versionに書き（x.y.zはリリースのバージョンを表します）、公開するサイトをsitesに並べます。repositoryはチームのリポジトリのowner/repo、sourcePathはそのルートからのディレクトリのパスです。バケットの名前がartifact-pagesでなければbucketも書きます（「cloudflare」を参照）。

    artifact-pages.yaml / acme/platform-admin
    schemaVersion: 1
web:
  version: x.y.z   # 手順3で置く閲覧アプリのリリース
provider: cloudflare
cloudflare:
  accountId: "<32文字のアカウントID>"
  zoneId: "<32文字のゾーンID>"
  publicBaseURL: https://docs.example.com
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

  3. 閲覧アプリを置く

    管理リポジトリで、管理者の認証情報を環境変数に入れて実行します。web.versionで指定したリリースの閲覧アプリを取得して検証し、バケットに書き込みます。ここで使うほかのコマンドと同じく、--dry-runを付けると書き込まずに変更計画だけを表示します。

    ターミナル / acme/platform-admin
    # 値はファイルに書かず、環境変数で渡す
$ export CF_R2_ACCESS_KEY_ID=… CF_R2_SECRET_ACCESS_KEY=… CF_API_TOKEN=…
$ artifact-pages app deploy --config artifact-pages.yaml --dry-run
$ artifact-pages app deploy --config artifact-pages.yaml

  4. サイトを登録する

    sitesの内容から、サイトの登録情報を配信先に書き込みます。これでサイトはできましたが、ページはまだありません。

    ターミナル / acme/platform-admin
    $ artifact-pages registry sync --config artifact-pages.yaml --dry-run
$ artifact-pages registry sync --config artifact-pages.yaml

  5. チームのリポジトリから公開する

    acme/checkoutのdocs/artifactsに、.htmlか.mdのページを1つ以上置きます。公開ではGitの履歴から日付を読むので、コミットが1つもないリポジトリでは失敗します。このリポジトリに設定ファイルは置かず、--configに管理リポジトリのファイルを指すgithub://の指定を渡します。?ref=で1つのコミットに固定することもできます。CLIは配信先の登録情報を読み、リポジトリとディレクトリが登録どおりかを確かめてから、ページをコピーしてサイトのインデックスを作ります。本文検索のためのデータも毎回作ります。

    ターミナル / acme/checkout
    $ artifact-pages site sync --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml --dry-run
$ artifact-pages site sync --site checkout --source docs/artifacts --config github://acme/platform-admin/artifact-pages.yaml

    必要な認証情報は、R2のアクセスキーとシークレット、サイトを変える実行で使うAPIトークンです。最初の1回は手元から実行してもかまいません。ふだんはマージ後にCIから実行します。そのまま使えるGitHub Actionsのワークフローが「サイトの公開」にあります。管理リポジトリが非公開なら、GITHUB_TOKENかGH_TOKENで読みます。

  6. ブラウザで開く

    https://docs.example.com/を開きます。サイトの一覧（Choose a site）にPayments / Checkoutが出るので、開いてページを選び、⌘⇧F / Ctrl ⇧ Fで本文検索も試してください。/checkout/payment-flow.mdのようなアドレスで再読み込みしても、手順1の配信のルールが閲覧アプリに渡します。

サイトを変えるときは、ディレクトリのファイルを編集または削除して、同じsite syncを実行します。変わったファイルをアップロードし、なくなったファイルを取り除きます。

ほかの配信先

どの配信先でも、使うコマンドと手順3から6は同じです。変わるのは、配信先の用意とartifact-pages.yamlのproviderの設定です。

  • AWSでは、S3とCloudFrontを用意し、provider: awsを設定します（「aws」を参照）。認証情報はAWSの標準の探し方に従い、CIではOIDCでロールを引き受けます。
  • 誰かが公開する前に、「信頼とアクセス制御」を読んでください。公開したHTMLはコードとして動き、読める人の制限は配信側で行います。
手元で試す（localプロバイダ）

localプロバイダは、クラウドのストレージの代わりにローカルのディレクトリへ書き込みます。アカウントなしで、ひとつのリポジトリに両方の役割を兼ねさせて流れを試せます。repositoryはチェックアウトのoriginと同じowner/repoにします。.local/の下は生成物なので、.gitignoreに加えておきます。

artifact-pages.yaml / acme/checkout
schemaVersion: 1
web:
  version: x.y.z   # 手順3で置く閲覧アプリのリリース
provider: local
local:
  root: .local/storage
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

手順3から5のコマンドは同じで、認証情報は要りません。--configにはartifact-pages.yamlを渡します。書き込まれたディレクトリを配信するには、/checkout/payment-flow.mdのようなアドレスを閲覧アプリに渡し、/_control/を返さないサーバーが要ります。nginxなら次のとおりです。

nginx.conf / acme/checkout
server {
  listen 80;
  root /usr/share/nginx/html;

  location = /_control { return 404; }
  location ^~ /_control/ { return 404; }
  location ^~ /_indexes/ { try_files $uri =404; }
  location ^~ /_artifacts/ { try_files $uri =404; }
  location ^~ /_previews/ { try_files $uri =404; }
  location ^~ /assets/ { try_files $uri =404; }
  location / { try_files $uri $uri/ /index.html; }
}
compose.yaml / acme/checkout
services:
  web:
    image: nginx:1.29-alpine
    ports:
      - "127.0.0.1:8080:80"
    volumes:
      - ./.local/storage:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
ターミナル / acme/checkout
$ docker compose up -d

http://localhost:8080/を開きます。これは試すための最小の設定です。サイトごとのCSPやキャッシュのヘッダーを含む例は、製品リポジトリのdocker/nginx/default.confにあります。最初からやり直すときは.local/storageを削除します。
