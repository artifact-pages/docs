はじめて導入する管理者向け

はじめる

artifact-pagesコマンドを入れ、管理リポジトリとチームのリポジトリがそれぞれ何をするかを確認してから、Gitのディレクトリにある文書を閲覧アプリで読むところまでを手元で試します。試すだけならクラウドのアカウントは要りません。

CLIを入れる

閲覧アプリの配置、サイトの登録、公開は、どれもartifact-pagesというひとつのコマンドで行います。リリースされたソースからビルドするGoのプログラムで、単体のバイナリは配布していません。

miseで入れる（おすすめ）

miseのGoバックエンドがgo installでコマンドをビルドし、選んだバージョンを管理します。-gを付けると、どのディレクトリでも使えるようにユーザー単位で入ります。

ターミナル / mise
$ mise use -g go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@x.y.z
$ artifact-pages version
  • バージョンは先頭のvを付けずに書きます（x.y.z）。mise ls-remote go:github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pagesで出る一覧と同じ形です。miseは新しいリリースを一定期間一覧に出さないため、出たばかりのリリースは載っていないことがあります。その場合も、GitHub Releasesで確認したバージョンを指定すれば入ります。
  • Go 1.26以降が必要です。Goがまだなければ、同じmise useにgo@1.26を加えると両方入ります。
  • artifact-pagesを呼び出せるのは、シェルでmiseを有効にしているとき（またはmiseのシムがPATHにあるとき）です。

go installで入れる

miseを使わずに同じリリースを入れる方法です。こちらはリリースのタグをそのまま、v付きで指定します。

ターミナル / go install
$ go install github.com/tasuku43/git-artifact-pages/cli/cmd/artifact-pages@vX.Y.Z

コマンドはGoのbinディレクトリ（go env GOBIN、未設定ならgo env GOPATHの下のbin）に入ります。PATHに含まれているか確認してください。x.y.zはリリースのバージョンを表します。リリースはGitHub Releasesで確認できます。Homebrewでの配布は予定していますが、まだ使えません。

バージョン

CLIのバージョンが、閲覧アプリのバージョンも決めます。artifact-pages versionには両方が出て、app deployは同じリリースのアプリを置きます。あとでアプリを別のリリースにするときは、そのリリースのCLIを入れてapp deployをもう一度実行します。

2種類のリポジトリ

ひとつの環境には、管理リポジトリがひとつと、チームのリポジトリがいくつでもあります。どのサイトを置くかは管理者が決め、各チームは自分のサイトだけを公開します。

  1. 管理リポジトリ

    artifact-pages.yamlに配信先とサイトの一覧を書きます。

  2. app deploy

    閲覧アプリを配信先に置きます。

  3. registry register

    サイトの登録情報を配信先に書きます。

  4. チームのリポジトリ

    マージ後に自分のCIからsite publishを実行します。例は説明用のacme/checkoutです。

  5. 配信先が登録を確認

    チームの設定ではなく、配信先にある登録情報を読みます。一致しなければ書き込みません。

  6. 閲覧アプリで読む

    公開されたサイトを、置かれた閲覧アプリで読みます。

管理リポジトリ · 環境ごとにひとつ

環境全体を受け持つ

artifact-pages.yamlに、配信先と、登録するサイトの一覧をすべて書きます。app deployで閲覧アプリを置き、registry registerでサイトを登録します。どちらもレビューを通った変更から実行するのが望ましい運用です。

チームのリポジトリ · いくつでも · 1つ以上のサイトを公開

自分のサイトを公開する

登録されたディレクトリに文書を置き、自分のサイトにsite publishを実行します。ふつうはマージ後に自分のCIから動かします。必要なのは配信先の設定だけで、サイトの一覧は要りません。管理リポジトリのファイルはgithub://の指定で読めます。

あるリポジトリがそのサイトに公開してよいかは、チームの設定ファイルではなく、配信先にあるサイトの登録情報で決まります。試すときはひとつのリポジトリで両方の役割を兼ねられます。次の節はその形で進めます。

手元で試す

localプロバイダは、クラウドのストレージの代わりにローカルのディレクトリへすべてを書き込むので、アカウントなしで一連の流れを試せます。CLIのほかに、Git、GitHub Releasesから閲覧アプリを取得するためのネットワーク接続、結果を見るためのPython 3（または任意の静的ファイルサーバー）を用意してください。

  1. リポジトリを用意する

    originのリモートがGitHubにあるGitのチェックアウトに、.htmlか.mdのページを1つ以上置いたディレクトリを用意します。公開ではGitの履歴から日付を読むので、コミットが1つもないリポジトリでは失敗します。コミットが1つ以上あれば、ページ自体はコミットしていなくてもかまいません。例では説明用のacme/checkoutと、そのdocs/artifactsを使います。実際には自分のリポジトリのowner/repoとディレクトリに置き換えてください。

    ターミナル / acme/checkout
    $ mkdir -p docs/artifacts
$ printf '# Payment flow design\n\nHow a card payment moves through checkout.\n' > docs/artifacts/payment-flow.md
# まだコミットがないリポジトリのときだけ
$ git add -A && git commit -m "Add a first page"

  2. artifact-pages.yamlを書く

    リポジトリのルートに置き、配信先にlocalを指定して、サイトを1つ登録します。repositoryはチェックアウトのoriginと同じowner/repoに、sourcePathはルートからのディレクトリのパスにします。.local/の下はすべて生成物なので、.gitignoreに加えておきます。

    artifact-pages.yaml / acme/checkout
    schemaVersion: 1
provider: local
local:
  root: .local/storage
sites:
  checkout:
    name: Payments / Checkout
    repository: acme/checkout
    sourcePath: docs/artifacts

  3. 閲覧アプリを置く

    CLIと同じリリースの閲覧アプリを取得して検証し、index.htmlとassets/を.local/storageに書き込みます。ここで使うほかのコマンドと同じく、--dry-runを付けると書き込まずに変更計画だけを表示します。

    ターミナル / acme/checkout
    $ artifact-pages app deploy --config artifact-pages.yaml --dry-run
$ artifact-pages app deploy --config artifact-pages.yaml

  4. サイトを登録する

    sitesの内容から、サイトの登録情報を書き込みます。これでサイトはできましたが、ページはまだありません。

    ターミナル / acme/checkout
    $ artifact-pages registry register --config artifact-pages.yaml --dry-run
$ artifact-pages registry register --config artifact-pages.yaml

  5. 公開する

    リポジトリとディレクトリが登録どおりかを確かめてから、ページをコピーしてサイトのインデックスを作ります。--fulltextを付けると、本文検索のためのデータも作ります。同じコマンドをもう一度実行するとUP TO DATEと出ます。

    ターミナル / acme/checkout
    $ artifact-pages site publish --site checkout --source docs/artifacts --config artifact-pages.yaml --fulltext --dry-run
$ artifact-pages site publish --site checkout --source docs/artifacts --config artifact-pages.yaml --fulltext

  6. 閲覧アプリで開く

    ディレクトリを配信してhttp://localhost:8000/を開きます。サイトの一覧（Choose a site）にPayments / Checkoutが出るので、開いてページを選び、⌘⇧F / Ctrl ⇧ Fで本文検索も試してください。

    ターミナル / acme/checkout
    $ python3 -m http.server 8000 --directory .local/storage
確認

http://localhost:8000/から開き、アプリの中で移動してください。この簡易サーバーはファイルを返すだけなので、/checkout/payment-flow.mdのようなアドレスで再読み込みすると404になります。本番用に設定した配信先では、こうしたアドレスも閲覧アプリに渡ります。

--fulltextは公開のたびに付けてください。付けずに公開すると、そのサイトの検索データが消えます。

サイトを変えるときは、ディレクトリのファイルを編集または削除して、同じsite publishを実行します。変わったファイルをアップロードし、なくなったファイルを取り除きます。最初からやり直すときは.local/storageを削除します。

本番の配信先に移る

使うコマンドは同じです。変わるのは書き込む先と、誰が実行するかです。

  • ストレージとCDNは、プロバイダ側で用意します。AWSならS3とCloudFront、CloudflareならR2とCloudflareのキャッシュです。Artifact Pagesはこれらを作りません。用意できたら、管理リポジトリのファイルのproviderとその設定を切り替えます（「配信先」を参照）。
  • 管理リポジトリからは、app deployとregistry registerを管理者の認証情報で実行します。認証情報は環境変数から渡し、ファイルには書きません（「認証情報」を参照）。
  • チームのリポジトリからは、マージ後にCIから、そのサイトにだけ書き込める認証情報で公開します。「サイトの公開」に、そのまま使い始められるGitHub Actionsのワークフローがあります。
  • 誰かが公開する前に、「信頼とアクセス制御」を読んでください。公開したHTMLはコードとして動き、読める人の制限は配信側で行います。
