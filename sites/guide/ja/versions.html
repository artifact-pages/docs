バージョンの固定と更新

運用中の環境が使うCLIと閲覧アプリのバージョンは、管理リポジトリの設定ファイルに書きます。変更は1か所で行い、プルリクエストで確認すれば、各サイトは次の実行から自動でそれに従います。このページでは、バージョンの固定、更新の手順、互換性のない変更があるときの進め方を説明します。

バージョンを持つもの

バージョンを持つ部品は3種類あり、それぞれ別のタグ系列でリリースされます。1つをリリースしても、ほかは変わりません。

部品タグ役割バージョンを決めるもの
CLIvX.Y.Zサイトを公開し、閲覧アプリを置くartifact-pagesコマンド。設定ファイルのcli.version
閲覧アプリ（web）web/vX.Y.Zapp deployが読者向けに置くバンドル。設定ファイルのweb.version
GitHub Action（それぞれ）publish-action/vX.Y.Z、preview-action/…、registry-action/…、app-deploy-action/…ワークフローからCLIを動かす薄いラッパー。ワークフローではartifact-pages/publish-action@vX.Y.Zのように参照します。ワークフローのファイル

CLIと閲覧アプリのリリースは、製品リポジトリのGitHub Releasesで確認できます。各Actionは専用のリポジトリでリリースされ、そこでのタグはvX.Y.Zの形です。このページのx.y.zはリリースのバージョンを表します。

組み合わせて使えるかどうかは、バージョンの数字からは判断しません。CLIと閲覧アプリはそれぞれ、書き込むデータ形式と読めるデータ形式を持っています。ストレージには実際に書き込まれたもの、置かれているものが記録され、コマンドがそれらを突き合わせます。製品が0.xのあいだは互換性を約束しないため、この確認が唯一の防御です。

設定ファイルで固定する

管理リポジトリのartifact-pages.yamlにcliとwebを足します。

artifact-pages.yaml / acme/platform-admin
schemaVersion: 1
cli:
  version: x.y.z   # すべての実行が使うCLI
web:
  version: x.y.z   # app deployが置く閲覧アプリ
provider: cloudflare
# ... プロバイダーの設定とsitesは通常どおり
  • 正確なバージョンだけを書けます。MAJOR.MINOR.PATCHの形にします。先頭のv、範囲指定、latest、プレリリースやビルドの接尾辞は受け付けず、終了コード2で失敗します。
  • それぞれのキーは1つのファイルにだけ書きます。設定ファイルを重ね合わせる場合、cliとwebを書けるのは多くても1つのファイルです。2つのファイルが同じ値でもエラーになります。1つのファイルに両方を書くのは問題ありません。置き場所は管理リポジトリの設定ファイルが自然です。
  • cli.versionが、実行されるCLIを決めます。インストール済みのartifact-pagesは、まず設定ファイルを読みます。別のリリースが書かれていれば、そのリリースをダウンロードしてチェックサムを検証し、同じ引数で実行し直します。対象はapp、site、registry、preview、lock、config checkです。cli.versionがなければ、インストール済みのCLIがそのまま動きます。
  • web.versionが、閲覧アプリを決めます。app deployは、製品リポジトリのリリースweb/vX.Y.Zを取得して検証し、配置します。取得先は公式のリリースに限られます。
  • どちらかを書いた設定は、固定されたものとして扱われます。その場合、後述の互換性の確認が有効になります。

サイトが追従するしくみ

サイトのリポジトリは、CLIを選びません。サイトのワークフローは、次のsite sync（ほかのページではまだ改訂前のsite publishという名前で書かれています）やpreview publishで、github://の指定で参照している管理リポジトリの設定ファイルを読み、そこに書かれたCLIで動きます。cli.versionを1回上げるだけで、各Actionの対応する範囲内であれば全サイトが移り、サイトのリポジトリにプルリクエストを出す必要はありません（後の節）。

  • 書き込む側は、配置済みの閲覧アプリを確認します。registry sync、site sync、preview publishは、配置済みの閲覧アプリが読めるデータ形式を調べ、そのCLIが書く形式を読めなければ、書き込む前に止まります。そのため、閲覧アプリに表示できないページを新しいCLIが公開することはありません。ただし、registry sync --accept-breakingで明示的に受け入れた場合は別です（後の節）。閲覧アプリがまだ置かれていないときは、web.versionのリリースのマニフェストに書かれた形式と照合します。レガシーの設定ファイルは確認されません。
  • プレビューでCLIを変えることはできません。プレビューのActionは、信頼の事前確認のあとでCLIを決め、リポジトリが持つ設定ファイルは信頼できるベースのコミットから読みます。そのため、プルリクエストで書き換えても、動くCLIは変わりません。明示的に指定した外部の管理者用ファイルとリモートの指定は、それ自身の権限で読まれます。

Actionのバージョンの意味

Actionのバージョンは、どのCLIが動くかを決めなくなりました。Actionの各リリースには、最初にインストールするブートストラップのCLIと、対応するCLIの範囲（cliRange。例は>=0.1.0 <0.2.0）が記録されています。ブートストラップのCLIが設定ファイルを読み、そこに書かれたCLIに切り替えます。

  • Actionはこれまでどおり、正確なタグで固定します。コミットSHAを40文字で書く固定でも、同じリリースの情報が固定されます。書き方は「サイトの公開」にあります。固定されるのは、ブートストラップのCLIと範囲です。
  • Actionを更新するのは、必要なときだけです。使いたいCLIがActionの範囲の外にあるときが、それにあたります。その場合、実行はダウンロードの前に、バージョンと範囲を示して終了コード2で失敗します。先に、範囲の広いActionのリリースに移ってから、cli.versionを上げてください。
  • 実行のたびに、動いたCLIが記録されます。Job SummaryのCLI executedに、実際に動いたバージョンが出ます。CLIをインストールできなかったときは、CLI executed: none (installation failed)になります。

更新する

データ形式がそのまま読めるリリースへの更新は、管理リポジトリの設定ファイルの変更で済みます。

  1. プルリクエストでバージョンを上げる

    管理リポジトリでcli.version、web.version、またはその両方を変えます。最新に保つ作業は、管理リポジトリ側で行ってください。このプルリクエストは、リポジトリに置いた更新用のボットに出させることもできます。

  2. CIでconfig checkを実行する

    設定ファイルに書かれたCLIで動きます。新しい閲覧アプリが、そのCLIの書くすべての形式と、レジストリと各サイトについてストレージに記録されたすべての形式を読めなければ、何も書かずに失敗します。再公開が必要なサイトは一覧に出ます。web.versionが必要で、なければ終了コード2になります。

    CI / acme/platform-admin
    $ artifact-pages config check --config artifact-pages.yaml

  3. マージしたら反映する

    registry syncを実行し、web.versionを変えたときは続けてapp deployも実行します。先に--dry-runで計画を確認できます。

    CI / acme/platform-admin
    $ artifact-pages registry sync --config artifact-pages.yaml
$ artifact-pages app deploy --config artifact-pages.yaml

  4. サイトが追従する

    各サイトは、次の同期かプレビューから新しいCLIを使います。サイトのリポジトリでの作業は要りません。ただし、新しいCLIがActionの範囲の外にあるときは別です（前の節）。

app deployは、書き込む前に逆向きの確認もします。配置する閲覧アプリが、レジストリと登録済みのすべてのサイトについてストレージに記録された形式をすべて読めなければなりません。記録がない、途中のまま、または閲覧アプリが読めない形式が記録されているときはコマンドが失敗し、再公開が必要なレジストリやサイトを一覧で示します。

互換性のないデータ形式の変更

リリースによっては、配置済みの閲覧アプリが読めないデータ形式に変わります。通常の確認はこれを意図的に拒否し、config checkも失敗するのが想定どおりなので、この経路ではconfig checkを実行しません。次の3つの手順が、その代わりになります。次の順序で明示的に受け入れてください。

  1. registry sync --accept-breaking

    配置済みの閲覧アプリがまだ読めない形式でも、新しいCLIがレジストリを書き込めるようにします。

  2. app deploy --accept-breaking

    保存済みのサイトやレジストリが、新しい閲覧アプリの読める形式になっていなくても、新しいアプリを配置します。記録がないものや途中のものも対象です。

  3. すべてのサイトを再公開する

    サイトごとに、新しいCLIでsite syncを実行します。

読者に見えます

再公開するまで、そのサイトを開いた読者には「needs to be republished」（再公開が必要）という表示が出ます。3つの手順はまとめて計画し、すぐに再公開してください。

--accept-breakingがあるのはregistry syncとapp deployだけです。schemaVersionに対応していないバージョン記録は、このオプションでも受け入れられません。registry syncは、途中のまま残った記録も受け入れません。site syncとpreview publishには、このオプションがありません。

1回だけ別のCLIで動かす

特定のサイトでリリースを試すときや、緊急のときは、設定ファイルのcli.versionを1回の実行だけ上書きできます。次のどれかを使います。

指定する場所書き方
CLIのフラグ--cli-version x.y.z（コマンド名の前でも後でもかまいません）
環境変数ARTIFACT_PAGES_CLI_VERSION=x.y.z
Actionの入力cli-version: x.y.z
  • 優先順位は、フラグ、環境変数、Actionの入力、設定ファイルの順です。値は正確なリリースのバージョンでなければならず、そうでなければ終了コード2になります。
  • 上書きしても、確認は省かれません。変わるのは動くCLIだけで、そのCLIが同じ設定ファイルとストレージを読み、同じ互換性の確認を行います。
  • Actionの範囲内でなければなりません。範囲の外なら、ダウンロードの前に終了コード2で失敗します。
  • 上書きは記録に残ります。Job SummaryにCLI overrideが加わり、指定の経路と、設定ファイルにバージョンがあればそのバージョンが出ます。

固定していない環境

cliもwebも書いていない設定ファイルは、従来の形（レガシー）として扱われます。ストレージに閲覧アプリのバージョン記録がないあいだは、固定しない従来の流れのままです。CLIの切り替えはなく、web.versionなしのapp deployは、そのCLI自身のリリースの閲覧アプリを、形式の確認なしで置きます。この経路が使えるのは、系列を分ける前のリリースだけです。それ以降のCLIのリリースには閲覧アプリのバンドルが含まれません。ストレージに閲覧アプリのバージョン記録ができたあとは、設定ファイルの内容にかかわらず確認が有効になります。

  • 固定を始めるときは、web.versionも書きます。cli.versionだけを書いてweb.versionも--archiveも指定しないapp deployは、終了コード2で失敗します。web.versionのないconfig checkも同じです。
  • 先にActionとCLIを更新します。古いCLIは、知らないcliとwebのキーを受け付けません。これらを理解するリリースに移ってから、設定ファイルにキーを足してください。
  • 既存のサイトは、再公開するまで「不明」と扱われます。バージョン記録ができる前に書かれたデータには記録がないため、app deployとconfig checkは、該当するサイトを一覧にして失敗します。再公開すると記録が作られます。web.versionを書いたうえで、先に再公開してから配置します。registry sync、すべてのサイトのsite sync、app deployの順です（閲覧アプリの記録がないあいだ、書き込む側はweb.versionのリリースのマニフェストと照合します）。または、--accept-breakingを使う互換性のない変更の順序に従います。

acme/platform-adminは説明用の管理リポジトリです。x.y.zとvX.Y.Zは、実際のリリースのバージョンに置き換えてください。
