Cloudflareの準備

「はじめる」の手順1を詳しく説明するページです。配信先となるCloudflare R2のバケットとホスト名について、用意するもの、決めること、最初のapplyの前に確認することをまとめます。Terraformの入力項目はすべて製品のモジュールのREADMEに書かれているため、このページでは繰り返さず、そちらを案内します。

できあがるもの

製品のCloudflare用Terraformモジュールは、CLIが公開先として使う配信先を作ります。

  • 非公開のR2のバケットがひとつ。閲覧アプリ、サイトの登録情報、公開したページ、プレビューがここに入ります。
  • ホスト名。バケットを、読者が使うカスタムドメインにつなぎます。/_control/*を含め、条件に合わないパスは、保存されたオブジェクトではなく閲覧アプリに回します。
  • キャッシュとレスポンスのルール。キャッシュはオリジンのキャッシュヘッダーに従います。公開したHTMLとプレビューには、同じContent Security Policyがかかります。
  • 配信内容を変えない設定。このホスト名に限り、メールアドレスの難読化、Rocket Loader、Polishなど、レスポンスの本文を書き換えたり差し込んだりするCloudflareの機能をConfiguration Ruleで止めます。ページは公開したとおりに読者へ届きます。
  • プレビューの期限切れ。プレビューは、選んだ日数のあとにR2のライフサイクルルールで消えます。
  • r2.devは無効のまま。バケットのもうひとつの公開アドレスも管理し、無効に保ちます。ダッシュボードで有効にすると、プランの差分として見えます。

モジュールは、閲覧アプリの配置、サイトの登録、CLIの認証情報の作成、読める人の制限を行いません。これらは別の手順です。「はじめる」のapp deployとregistry sync、下の認証情報、「信頼とアクセス制御」を参照してください。

AWS

AWS（S3とCloudFront）の準備は、このガイドではまだ扱っていません。設定ファイルでのAWSの項目は「設定ファイル」にあります。

先に必要なもの

  • R2が使えるCloudflareアカウント。32文字のアカウントIDが必要です。
  • ホスト名を含むゾーン。読者が使うホスト名（例ではdocs.example.com）を含むDNSのゾーンが、そのアカウントにすでにある必要があります。32文字のゾーンIDが必要です。
  • TerraformとCloudflareプロバイダー。Terraformは>= 1.5.0, < 2.0.0、Cloudflareプロバイダーは>= 5.24.0, < 6.0.0に対応しています。
  • プレビューの保持期間の決定。preview_retention_daysは1から36500までの整数（日数）で、必須です。保持期間はTerraformだけにあり、CLIの設定ファイルには書きません。

認証情報

関わる認証情報は3つで、Terraformの実行とCLIで使い分けます。値は.tfファイル、変数ファイル、設定ファイル、リポジトリのどこにも書かず、シークレット管理の仕組みやCIのシークレットで渡してください。

認証情報使う場面必要な権限
Terraform用のCloudflare APIトークンTerraformの実行。プロバイダーがCLOUDFLARE_API_TOKENから読むアカウント: Workers R2 Storage Edit（バケット、カスタムドメイン、r2.devの設定、ライフサイクルルール）。ゾーン: Transform Rules Edit（リクエストとレスポンスヘッダーの変換）、Cache Rules Edit、Config Rules Edit。waf_custom_rulesを設定する場合はZone WAF Edit（モジュールのREADMEではZone WAF Write）も必要です。CLIの認証情報とは別のものです。
R2のアクセスキーとシークレットCLI。管理者のジョブとチームのジョブバケットの読み書き。設定で名前を変えない限り、CF_R2_ACCESS_KEY_IDとCF_R2_SECRET_ACCESS_KEYから読みます。
CLI用のCloudflare APIトークンCLI。キャッシュを消す必要がある実際の実行（site sync、registry sync、app deploy、内容を変える削除）ゾーンのキャッシュを消す権限（Cache Purge）。設定で名前を変えない限り、CF_API_TOKENから読みます。ドライランと、変更のない実行では不要です。
  • 管理者のジョブ（app deploy、registry sync）は、R2のキーとキャッシュを消すためのトークンを使います。
  • チームのジョブ（site sync）も同じ変数名を使いますが、渡す認証情報は自分のサイトのパスまで絞れます。内容を変える実際のsite syncには、キャッシュを消すトークンも必要です。preview publishに必要なのはR2のキーだけです（中断したpreview removeを再開する場合を除く）。どのコマンドがどの認証情報を使うか、登録情報の読み取り専用の認証情報を分ける方法は、「設定ファイル」にあります。
  • キーの組の代わりにトークン1つ。R2の2つの変数がどちらも未設定なら、CLIはAPIトークンだけを使えます。そのトークンには、対象のバケットのWorkers R2 Storage Bucket Item Writeと、ゾーンのCache Purgeの権限が必要です。CLI v0.2.0から使えます。この方式ではドライランも含め、毎回トークンを検証します。詳細は下にリンクした仕様書を参照してください。

チーム用に絞った認証情報のオブジェクト単位の権限は、製品リポジトリのCloudflare deployment（英語）にあります。トークン1つの設定は、仕様書の「Cloudflare account-token credentials」にあります。

モジュールを呼び出す

管理リポジトリ、またはその隣に、Cloudflare用のモジュールを呼び出す小さなTerraformのルートモジュールを書きます。次が最小の形で、bucket_nameは省略でき、既定はartifact-pagesです。sourceは、モジュールのパッケージ用リポジトリのリリースを指定しています。Terraform Registryでの公開は予定されており、公開後はこのページもRegistryのソースに切り替えます。

main.tf / acme/platform-admin
terraform {
  required_version = ">= 1.5.0, < 2.0.0"

  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = ">= 5.24.0, < 6.0.0"
    }
  }
}

module "artifact_pages" {
  source = "git::https://github.com/artifact-pages/terraform-cloudflare-artifact-pages.git?ref=v0.1.0"

  account_id             = var.cloudflare_account_id
  zone_id                = var.cloudflare_zone_id
  public_hostname        = var.public_hostname
  preview_retention_days = var.preview_retention_days
  # bucket_name = "artifact-pages"   # 省略可
}

provider "cloudflare" {}   # CLOUDFLARE_API_TOKENを読む

output "artifact_pages_deployment_config_yaml" {
  value = module.artifact_pages.artifact_pages_deployment_config_yaml
}

変数には、アカウントID、ゾーンID、スキーム・ポート・パスを含まないホスト名、保持日数を渡します。値はコミットしない変数ファイルに書いてください。入力項目の全体と、既定値や制約は、モジュールのREADMEのInputsの表（terraform-cloudflare-artifact-pages、英語）にあります。

applyの前にプランを確認する

まずterraform planを実行して中身を読みます。モジュールは設定のまとまりを丸ごと管理するため、すでにそのいくつかがあるゾーンやバケットでは、最初のapplyの前に対応が必要です。具体的な手順とインポートするアドレスは、モジュールのREADMEのResource ownership and apply reviewにあります。

  • ゾーンの既存のルール。モジュールは、ゾーンのtransform、cache、response-header、configurationの各ルールセットを丸ごと管理します。すでにあるものは、まず対応する*_ruleset_nameに現在の名前を設定し（ルールセットの名前は変更できず、違う名前にすると置き換えがプランされます）、次にインポートし、そのうえで既存のルールをすべて、同じ順序で対応するexisting_*_rulesに渡してください。そうしないと、最初のapplyが失敗するか、ルールが置き換わります。ダッシュボードは最初のConfiguration Ruleを作るときにconfigurationのルールセットも作るため、それも確認してください。waf_custom_rulesを設定する場合は、カスタムファイアウォールのルールセット（waf_custom_rules.ruleset_nameとexisting_rules）にも同じ扱いが必要です。こちらはprevent_destroyが設定されています。
  • バケットの名前。既定のartifact-pagesは予約されていません。同じ名前のバケットがアカウントにあると、作成に失敗します。モジュールは常にバケットを新しく作ります。既存のバケットを使う場合は、READMEの「Existing-bucket use」を参照してください。
  • カスタムドメイン。プロバイダーは、既存のR2のカスタムドメインをインポートできません。ホスト名がすでにつながっている場合はconnect_custom_domain = falseにし、その接続が有効で、望むTLSのバージョンであることを別に確認してください。
  • ライフサイクルルール。モジュールは、バケットのライフサイクルルールの全体を管理します。残したい他のルールはadditional_lifecycle_rulesに渡してください。プロバイダーはこのリソースのインポートも削除もできないため、Terraformから外してもルールはそのまま残ります。
  • r2.devは無効のまま。ダッシュボードで有効にすると、ホスト名の経路の振り分けを通らず、非公開の/_control/*のオブジェクトが見えてしまうおそれがあり、次のプランに差分が出ます。無効のままにしてください。
  • バケットは強制削除されません。削除する前に、中身を意図して空にするか移してください。モジュールを外してもバックアップにはならず、CLIが公開した内容が元に戻ることもありません。
  • 費用。R2のストレージとリクエスト、カスタムドメイン、ルールは課金の対象になりえ、ルールにはプランごとの上限もあります。モジュールはアカウントごとの料金を見積もらないため、利用中のプランの料金と上限を確認してください。
読める人

モジュールは、誰が読めるかを決めません。ホスト名の制限は、Cloudflare Accessなどのエッジのポリシーで別に行います。任意のwaf_custom_rulesで、IPアドレスの許可リストなど、ホスト名向けのルールを管理できますが、認証は設定しません。「信頼とアクセス制御」を参照してください。

出力からCLIの設定を埋める

applyのあと、モジュールの出力artifact_pages_deployment_config_yamlが、配信先のそのままコピーできるYAMLになります。含まれるのは秘密でない識別子と、実際のバケットの名前だけです。認証情報の変数名は、既定値（CF_R2_ACCESS_KEY_ID、CF_R2_SECRET_ACCESS_KEY、CF_API_TOKEN）なら省かれ、変更した場合に書き出されます。

ターミナル / acme/platform-admin
$ terraform output -raw artifact_pages_deployment_config_yaml
出力 / 説明用の値
"cloudflare":
  "accountId": "<32-character account ID>"
  "bucket": "artifact-pages"
  "publicBaseURL": "https://docs.example.com"
  "zoneId": "<32-character zone ID>"
"provider": "cloudflare"
"schemaVersion": 1

キーは引用符つきで、アルファベット順に出力されます。YAMLとしては正しいので、写すときに整えてください。モジュールの呼び出しでregistry_readerを設定した場合は、その環境変数名も出力されます。

これらのキーを管理リポジトリのartifact-pages.yamlに写し、「はじめる」の手順2のようにweb.versionとsitesを加えます。各キーの意味は「設定ファイル」にあります。認証情報の値は、管理者のジョブとチームのジョブの環境に置き、ファイルには書きません。

docs.example.comとプレースホルダーは説明用の例です。生成される値は公開されている識別子で、秘密ではないため、管理リポジトリにコミットできます。

次に進む

バケット、ホスト名、ルールの用意と設定ファイルの作成ができたら、「はじめる」の手順2に進み、閲覧アプリの配置とサイトの登録を行います。
